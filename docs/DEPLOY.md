# Deploy & DevOps — учебный гайд

Практический разбор деплоя nexo-assist с объяснением концепций (DevOps впервые).
На каждом шаге: **что** сделали, **зачем**, и **концепт простыми словами** + ссылки.
Высокоуровневый план — в [PRODUCT_PLAN.md §Фаза 5](PRODUCT_PLAN.md); здесь — «почему так».

## Куда деплоим (решено)

- **Приложение:** наш Docker-образ → **k3s** (лёгкий Kubernetes) на **Hetzner Cloud**
  (сервер **CX23**, Ubuntu 26.04, ~€6.5/мес). Настоящий k8s → максимум DevOps-опыта.
- **База:** managed Postgres — **Supabase** (free tier). Бэкапы/аптайм — на их стороне.
- **Портируемо:** апп = образ, БД = строка `DATABASE_URL`. Переезд на другой хост —
  смена таргета, не переписывание.

### Почему Hetzner, а не Oracle (история выбора)

Сначала целились в бесплатный **Oracle Cloud Always Free** (ARM-инстанс `A1`). Что там
пришлось настраивать и почему не взлетело:

- **VCN** (Virtual Cloud Network) — сеть для VM: адресное пространство + **публичная
  подсеть** + **Internet Gateway** (шлюз в интернет). Без неё у VM нет публичного IP и
  выхода в сеть. Oracle заставляет собирать это руками (через VCN Wizard).
- **Затык:** `A1` — «Out of capacity» во всех availability domains (бесплатный ARM вечно
  разобран), а home-регион сменить нельзя. Для беты, которую показываешь людям, — ненадёжно.

**Hetzner** такой возни не требует: **сеть и публичный IP готовы из коробки** (VCN
настраивать не нужно), инстанс поднимается сразу, стабильно, за небольшую плату. Пивот
ничего не стоил — образ и манифесты те же, сменился только хост (в этом и смысл
портируемости). Oracle остаётся как бесплатная альтернатива, если однажды отпустит A1.

## Как код попадает в прод (общая картина)

От мержа до работающего пода всё делает автоматика — руками запускать нечего:

```
мерж PR в dev
   │
   ├─► build-and-test ─ lint, типы, тесты, миграции, e2e (чистая машина + Postgres)
   │        ↓ только если зелёное
   ├─► docker-and-k8s ─ валидация манифестов → мультиарх-образ → GHCR sha-<коммит>
   │        ↓ только если зелёное
   └─► deploy ───────── SSH на сервер → deploy.sh: checkout коммита → пин его образа →
                        kubectl apply -k → rollout status → не поднялось =
                        автооткат и красная джоба
```

1. **Собираем образ** (Dockerfile) — самодостаточный «архив» приложения.
2. **Кладём в registry** (GitHub Container Registry) — склад образов, откуда кластер качает.
3. **Кластер применяет манифесты** (`kubectl apply -k k8s/`) — декларативно: ты
   описываешь _желаемое состояние_, k8s его достигает и поддерживает.

| Что                                     | Кто отвечает   | Где смотреть                        |
| --------------------------------------- | -------------- | ----------------------------------- |
| Тесты, сборка образа, деплой            | GitHub Actions | Actions → прогон коммита            |
| Хранение образов                        | GHCR           | GitHub → Packages                   |
| Запуск, миграции, перезапуски, здоровье | k3s на сервере | `npm run k8s:status`, `k8s:logs`    |
| База и бэкапы                           | Supabase       | панель Supabase                     |
| Ошибки приложения                       | Sentry         | панель Sentry                       |
| Алерты уровня кластера (под лежит)      | **никто**      | пробел, см. PRODUCT_PLAN «Осталось» |

Две вещи, которые легко упустить:

- **Деплоится только `dev`** (`if: github.ref == 'refs/heads/dev'`). Мерж в `main` соберёт
  образ, но в кластер он не поедет: окружение пока одно.
- **О провале деплоя узнаёшь из красной джобы** `deploy` (GitHub шлёт уведомление). Логи
  сломанного пода скрипт выгружает в лог джобы **до** отката — в кластере их уже не будет.

## Концепции простыми словами

- **Container / образ (image):** упакованное приложение + его зависимости. Образ —
  «слепок» (read-only), контейнер — запущенный экземпляр. У нас образ строит
  многостадийный [`Dockerfile`](../Dockerfile) (build → prune dev-deps → тонкий runtime).
- **Kubernetes (k8s):** система, которая запускает контейнеры, перезапускает упавшие,
  следит за здоровьем, обновляет без простоя. **k3s** — его лёгкая версия для одной
  небольшой VM.
- **Pod** — минимальная единица запуска: один (или несколько) контейнеров вместе. Наш
  Pod = бот (+ initContainer миграций, см. ниже).
- **Deployment** — «хочу N одинаковых Pod'ов такой-то версии». Держит их живыми,
  катит обновления. У нас `replicas: 1` (бот на long-polling — singleton: один поллер
  на токен, иначе Telegram шлёт 409).
- **Service** — стабильный внутренний адрес к Pod'ам (они эфемерны, IP меняются).
- **ConfigMap vs Secret** — конфиг через env-переменные. Несекретное (порты, cron) →
  **ConfigMap**; секреты (токен бота, пароль БД в `DATABASE_URL`) → **Secret**
  (не коммитим в репо!).
- **initContainer** — контейнер, который отрабатывает **до** основного и должен
  успешно завершиться. Идеален для миграций БД: применили схему → только потом
  стартует апп.
- **Probes (пробы):** k8s спрашивает приложение о здоровье. _liveness_ — «живой?»
  (нет → перезапуск); _readiness_ — «готов принимать трафик?» (нет → убирают из
  Service); _startup_ — даёт время на медленный старт.
- **Kustomize** — накладывает манифесты без шаблонов (в отличие от Helm). `kubectl -k`
  умеет это из коробки. Наш [`k8s/kustomization.yaml`](../k8s/kustomization.yaml)
  собирает configmap + db-ca + deployment + service.
- **Registry (GHCR)** — хранилище образов. CD пушит туда `nexo-assist:<sha>` и
  прописывает этот тег в деплой.

## Разбор каждого DevOps-файла (как работает / что делать тебе)

### `Dockerfile` — как собирается образ

Мультистейдж: **build** (ставит все зависимости, `npm run build` → TS в `dist`, затем
`npm prune --omit=dev` выкидывает dev-пакеты) → **dev** (для docker-compose hot-reload)
→ **runtime** (финальный: только `dist` + prod `node_modules`, не-root юзер `node`,
`HEALTHCHECK`). Тонкий и без dev-инструментов — поэтому миграции гоняем компилированным
data-source (Шаг 1).

- **Тебе:** ничего — образ собирает CI (5a). При желании локально: `docker build --target runtime -t nexo-assist .`.

### `.dockerignore` — что не попадает в образ

Исключает `node_modules`, `dist`, `.git`, `test`, `*.md`, `.env*` (кроме `.env.example`).
→ образ меньше и **`.env` с секретами не утекает** внутрь образа.

- **Тебе:** ничего.

### `docker-compose.yml` — локальный стек (не для прода)

Сервисы `app` (runtime-образ) + `postgres` (17-alpine, том `pgdata`, healthcheck). `app`
ждёт, пока БД healthy; env заданы прямо тут. Это **локальная** сборка, не деплой-артефакт.

- **Тебе:** `npm run db:up` — поднять только Postgres (обычный дев — `npm run start:dev` на хосте).

### `docker-compose.override.yml` — локальный дев с hot-reload

Автомёржится при `docker compose up`. Стадия `dev`, бинд-маунт исходников (`.:/app`,
`node_modules` из образа), гоняет миграции и `start:dev` (watch — код меняется → перезапуск).

- **Тебе:** `npm run dev:docker` — весь стек (БД + апп) в докере с автоперезагрузкой.

### `k8s/deployment.yaml` — как приложение живёт в кластере

1 реплика (singleton — один поллер на токен), стратегия `Recreate`, **initContainer
`migrate`** (миграции до старта), пробы (live/ready/startup), ресурс-лимиты, hardening
(non-root, read-only rootfs, drop caps), `envFrom` (configmap + secret). Детали —
в «Концепциях» и Шаге 2.

- **Тебе:** в самом файле — ничего; при деплое создаёшь Secret и пинишь образ (§4.6).

### `k8s/configmap.yaml` — несекретные настройки

Все несекретные env: `APP_ENV`, `PORT`, `WATCH_*`, `THROTTLE_*`, `LOG_LEVEL`,
`CORS_ORIGIN`, `ADMIN_TELEGRAM_ID`, (закомментирован `OTEL_*`).

- **Тебе:** по желанию подправить значения (напр. `WATCH_CRON`, `CORS_ORIGIN` — сузить
  до своего домена в проде). `ADMIN_TELEGRAM_ID` — твой id (уже стоит). **Секреты сюда не клади.**

### `k8s/service.yaml` — внутренний адрес

`ClusterIP` :80 → контейнер :3000. Нужен для доступа **внутри** кластера (скрейп
`/metrics` Прометеем, health). Наружу бота не публикуем (long-polling ходит сам).

- **Тебе:** ничего.

### `k8s/kustomization.yaml` — что собрать вместе

Объединяет configmap + deployment + service; сюда добавляется блок `images:` для пина
образа по sha (пинит оба контейнера — app и initContainer).

- **Тебе:** ничего. `deploy.sh` сам переписывает `newTag` на sha деплоя; закоммиченный
  тег — устаревший плейсхолдер, поэтому перед ручным `apply` его нужно запинить
  (рецепт — в [`k8s/README.md`](../k8s/README.md)).

### `k8s/README.md` — краткий справочник по манифестам

Что за файлы + как создать Secret.

- **Тебе:** прочитать перед первым деплоем.

### `.github/workflows/ci.yml` — CI и CD

Три джобы: **build-and-test** (lint / format / typecheck / knip / юниты / build /
миграции / e2e против сервиса Postgres), **docker-and-k8s** (валидирует манифесты,
собирает мультиарх-образ, пушит в GHCR на push в `dev`/`main`) и **deploy** — только на
push в `dev`, выкатывает этот же коммит в кластер (Шаг 5b).

Верхний `concurrency` отменяет устаревшие прогоны, **кроме `dev`**: там отмена оборвала бы
SSH-сессию посреди деплоя, и `deploy.sh` не успел бы откатиться — бот остался бы лежать.

- **Тебе:** ничего — работает само. Результат: Actions → прогон мержа.

### npm-скрипты (DevOps)

`db:up` / `db:down` / `db:reset` (докер-Postgres), `migration:run|generate|revert|show`
(локально, ts-node), `migration:run:prod` (в контейнере, чистый node), `dev:docker`
(полный стек), `build`, `start:prod`.

- **Тебе:** для локали — `db:up` + `start:dev`, либо `dev:docker`.

## Шаги (лог с пояснениями)

### Шаг 1 — миграции, работающие и локально, и в контейнере

**Проблема:** миграции запускались только через `ts-node` по исходникам `src/`. В
рантайм-образе нет ни `ts-node`, ни `src/` (только компилированный `dist/`) → в проде
не прогнались бы.

**Решение:** один `data-source.ts`, который сам определяет по расширению своего файла,
где он запущен — `.ts` (локально, ts-node, `src/`) или `.js` (в контейнере, node,
`dist/`). Убрали dev-зависимость `dotenv` из него (в проде env приходит из окружения
пода). Добавили prod-скрипт `migration:run:prod` (чистый `node`, без ts-node).

**Концепт — почему миграции отдельно от кода:** схема БД версионируется миграциями
(каждая — один необратимый шаг), а `synchronize` в проде запрещён (он молча меняет
схему). Так изменения БД предсказуемы и повторяемы.

### Шаг 2 — миграции при деплое (initContainer) + секреты

**Что:** в Deployment добавлен initContainer `migrate` — тот же образ, прогоняет
миграции (той же командой, что `migration:run:prod`) до старта бота. Упал → Pod не поднимется (не работаем на битой
схеме). `DATABASE_URL` кладётся в Secret (в нём пароль БД), а не в ConfigMap.

**Концепт — почему initContainer, а не «внутри приложения»:** миграции отделены от
рантайма — приложение не должно менять схему при каждом старте (гонки при нескольких
репликах, права). initContainer прогоняет их один раз, атомарно, до апп-контейнера.
Идемпотентно: TypeORM хранит применённые миграции в таблице и пропускает их повторно.

**Концепт — ConfigMap vs Secret:** `DATABASE_URL` содержит пароль → это секрет.
Secret в кластере не коммитится; для GitOps используют sealed-secrets / external-secrets
оператор или секрет-менеджер платформы.

### Шаг 3 — верификация TLS-сертификата к базе

**Что:** проверка сертификата БД включается через `sslmode=verify-full` в
`DATABASE_URL` (§4.2). Драйвер `pg` отдаёт управление SSL строке подключения, когда в
ней есть `sslmode`, поэтому именно URL — источник правды; в `app.module.ts` оставлен
запасной `rejectUnauthorized: true` (если URL вдруг без `sslmode`), а локально TLS
выключен (Docker-Postgres).

**Концепт — шифрование ≠ аутентификация.** Просто шифрование не проверяет, _с кем_
говорим — можно подставить свой сертификат (MITM) и читать/подменять трафик (пароли,
данные). `verify-full` проверяет, что серт выдан доверенным CA **и** валиден для этого
хоста. Значит нужен **корень доверия**: Supabase подписывает своим собственным корневым
сертификатом, которого в наборе Node нет, — поэтому мы возим его в репозитории
([`k8s/db-ca-configmap.yaml`](../k8s/db-ca-configmap.yaml), см. учебный инцидент ниже). (Берём
`verify-full`, а не `require`: `require` в новых версиях `pg` перестанет проверять серт.)

### Шаг 5a — CI: сборка и публикация образа в GHCR

**Что:** в `.github/workflows/ci.yml` джоба `docker-and-k8s` теперь собирает образ и
пушит его в **GHCR** (`ghcr.io/<owner>/nexo-assist`). На PR — только сборка (проверка
Dockerfile), на push в `dev`/`main` — сборка + пуш. Теги: `sha-<commit>` (неизменяемый),
имя ветки, `latest` (на `main`). Аутентификация — встроенным `GITHUB_TOKEN` (право
`packages: write`), отдельный секрет не нужен. Образ **мультиарх** (`amd64` + `arm64`),
т.к. VM на Oracle — ARM (Ampere); `amd64` оставлен для локальной разработки.

**Концепт — зачем registry и почему деплоим по sha.** Кластер не собирает код — он
тянет готовый образ из registry (GHCR). Тег `latest` удобен, но «плавающий» (сегодня
один образ, завтра другой) → для деплоя пинуем **неизменяемый** `sha-<commit>`: точно
знаешь, что запущено, и откат = просто прежний sha. gha-кэш ускоряет пересборку.

### Шаг 5b — CD: автодеплой в кластер

**Что:** мерж в `dev` → CI прогоняет тесты, собирает образ, и джоба `deploy` выкатывает
**тот же коммит** в кластер. Руками больше ничего (ни туннеля, ни `kubectl`).

**Как GitHub попадает на сервер, ничего не открывая наружу:**

- Отдельный SSH-ключ **только для деплоя**; приватная часть — в GitHub Secret `CD_SSH_KEY`,
  адрес хоста — в `CD_HOST` (чтобы сменить сервер, не трогая код).
- **Ротация CD-ключа.** На сервере: `rm /root/cd_key /root/cd_key.pub`, затем `setup-server.sh` —
  он сгенерирует новый и **перезапишет** `authorized_keys` (там ровно одна строка, только
  CD-ключ; добавленное руками пропадёт, скрипт об этом сообщает). Новый приватный ключ, путь
  которого он напечатает, положи в `CD_SSH_KEY`. Раньше сторож смотрел на _комментарий_ внутри
  ключа — тот при перегенерации не меняется, поэтому старый ключ оставался разрешённым, то есть
  ротация ничего не меняла.
- **CI проверяет, что подключился именно к нашему серверу** — сверяет его «ключ хоста» с
  заранее записанным в `CD_HOST_KEY`. Ключ хоста — это удостоверение сервера: он предъявляет
  его каждому, кто подключается. Раньше мы делали `ssh-keyscan`, то есть спрашивали у того,
  кто ответил, кто он такой, и верили ответу — это не проверка. Кто сумел бы вклиниться в
  соединение, принял бы наш деплой и отрапортовал «готово»: приватный ключ не утекает (SSH его
  не передаёт), но CI показал бы зелёный деплой, которого не было. Значение печатает
  `setup-server.sh` на самом сервере — в момент, когда ты уже ему доверяешь.
  **Пересоздал сервер — ключ сменился, обнови секрет.**
- На сервере — пользователь `deploy` **без sudo**, а ключ в его `authorized_keys` прописан с
  `command="/usr/local/bin/deploy.sh"`, без шелла и проброса портов. Проверено: попытка
  выполнить произвольную команду отклоняется. Утёкший ключ = «кнопка деплоя», не доступ к серверу.
- Джоба идёт **только на push в `dev`** — PR из форка её не запустит (иначе чужой код получил бы
  доступ к кластеру; поэтому же на публичном репозитории нельзя self-hosted runner).

**Что делает [`deploy/deploy.sh`](../deploy/deploy.sh):** валидирует sha (строго hex — строка
попадает в команды, иначе возможна инъекция) → переключает копию репозитория на этот коммит →
пинит образ этого же коммита → **сверяет пин** → `kubectl apply -k` → ждёт `rollout status`;
**не поднялся — автоматически откатывается** на предыдущую версию, и джоба красная.

**Почему пин сверяется.** Тег образа подставляется в манифест обычной заменой текста (`sed`), а
`sed` при несовпадении **ничего не делает и сообщает об успехе**. Тогда бы выкатился тег, лежавший
в файле раньше: джоба зелёная, под поднялся, откат не сработал (ничего же не упало) — а в проде
не тот код, который ты смержил. Заметить такое можно только случайно.

Поэтому после замены скрипт **отрисовывает** манифесты (`kubectl kustomize`) и проверяет, что
разворачивается именно образ этого коммита. Проверяется результат, а не текст файла: `sed`
переписывает все строки с `newTag:`, включая закомментированные, — по файлу проверка прошла бы,
а поехал бы не тот образ.

Увидел в красной джобе `deploy: rendered manifests don't all use …` — значит **ничего не
применялось, прод не тронут**. Разошлись имена образа: смотреть `newTag`/`newName` в
[`k8s/kustomization.yaml`](../k8s/kustomization.yaml) и строки `image:` в
[`k8s/deployment.yaml`](../k8s/deployment.yaml) — kustomize подменяет их по совпадению имени,
поэтому переименование с любой стороны рвёт связь. Привести в соответствие и запустить заново.

**Почему откат обязателен именно у нас.** Реплика одна, стратегия `Recreate` — старый под
гасится **до** запуска нового. Значит неудачный деплой оставляет бота лежать, а деплой
автоматический: никто не обязан в этот момент смотреть в консоль. `rollout undo` возвращает
последний шаблон пода, который реально работал, — бот поднимается сам, суммарно до ~3 минут
(до 180 с на то, чтобы понять, что новый под не встал, плюс запуск старого).

**Где искать причину.** Откат гасит сломанный под, вместе с ним исчезают его логи — поэтому
скрипт **до** отката выгружает `describe pod` и логи всех контейнеров в лог CD-джобы. Смотреть
надо туда (Actions → упавший запуск), а не в кластер: там уже работает старая версия.

**Почему запускаемая копия скрипта лежит в `/usr/local/bin`, а не в папке репозитория:** скрипт
сам переключает эту папку на другой коммит, а bash читает файл по мере выполнения — подмена
на лету ломает исполнение. Канонично скрипт живёт в репо (ревью, история), исполняется — копия.
Изменил скрипт → **закоммить и запушь в `dev`**, затем переустанови (`setup-server.sh`): он
ставит то, что лежит в `origin/dev`, а не локальную правку.

**Откат.** При неудачном деплое происходит **сам**. Вручную нужен, только если проблему
заметили уже после успешного старта (бот поднялся, но ведёт себя не так):

```bash
# 1. Вернуть предыдущий под средствами k8s (быстро, без сборки):
k3s kubectl rollout undo deployment/nexo-assist

# 2. Или выкатить конкретный прошлый коммит (его образ уже лежит в GHCR):
sudo -u deploy /usr/local/bin/deploy.sh <sha>
```

**Важно: откат возвращает под, но не базу и не конфиг.** `rollout undo` умеет вернуть только
**шаблон пода** (образ и его настройки). Всё, что живёт рядом, остаётся новым:

- **База.** Миграции применяет initContainer **до** старта приложения, и применённая миграция
  остаётся применённой — старый код поедет на новой схеме. Для добавляющих миграций (новая
  колонка, новая таблица) это безопасно: старый код их просто не замечает. Для разрушающих
  (удалить/переименовать колонку) — нет, нужен ручной откат: `npm run migration:revert`
  **с локальной машины**, подставив в `.env` прод-`DATABASE_URL` (Supabase доступен извне;
  внутри контейнера этой команды нет — там только `migration:run:prod`).
  Практический вывод: **разрушительные изменения схемы делаем в два релиза** — сначала
  выкатываем код, не зависящий от старой колонки, и только следующим релизом её удаляем.
- **ConfigMap/Secret.** Имя у ConfigMap фиксированное, поэтому `apply -k` перезаписал его
  на месте, и откат пода старые значения не вернёт. Если деплой сломала правка конфига,
  автооткат не спасёт — правь конфиг и деплой заново. (Как чинится по-настоящему —
  `configMapGenerator` с хешем в имени; записано в техбэклог PRODUCT_PLAN.)

**Ограничения текущей схемы** (осознанные, см. PRODUCT_PLAN): гейта
подтверждения нет — любой мерж в `dev` едет в прод. При разделении dev/prod для `main`
стоит добавить подтверждение, а при росте числа сервисов — присмотреться к GitOps
(ArgoCD/Flux): кластер сам тянет состояние из git, входящий доступ не нужен вовсе.

**Переезд на другой хост** = поднять k3s (§4.4) и выполнить:

```bash
sudo bash deploy/setup-server.sh   # пользователь, доступ к кластеру, чекаут, скрипт, CD-ключ,
                                   # + отключение входа по паролю и fail2ban (шаг 6)
```

затем положить новый приватный ключ в `CD_SSH_KEY`, новый адрес в `CD_HOST` и **новый ключ
хоста** в `CD_HOST_KEY` (путь к ключу и ключ хоста печатает скрипт, адрес — из консоли
провайдера; ветку, с которой ставится `deploy.sh`, задаёт `REPO_REF`, по умолчанию `dev`) —
у нового сервера ключ хоста другой, иначе
первый же деплой упадёт на проверке. Скрипт идемпотентный — повторный запуск безопасен.

## Шаг 4 — Runbook: поднять кластер и задеплоить

Среда уже поднята в этом порядке — держим его для **пересоздания или переезда** (и как
карту, что где живёт). Пока — **только prod**, деплой в namespace `default`. Бот на
long-polling ходит наружу сам, поэтому **входящие порты для бота не нужны** (ни ingress,
ни домен). На всё — ~1 час.

### 4.0 Что нужно локально (prerequisites)

- `kubectl` (проверь: `kubectl version --client`), `ssh`, `git`.
- Аккаунт GitHub (образ попадает в GHCR после мержа в `dev` — шаг 5a).
- SSH-ключ (`ssh-keygen`, если нет) — публичную часть добавишь на сервер при создании.

### 4.1 Hetzner Cloud — сервер

1. Hetzner Console → Add Server: **Ubuntu 26.04**, тип **CX23**, регион в ЕС, свой
   SSH-ключ. Сеть и публичный IP выдаются из коробки — настраивать нечего.
2. Запиши публичный IP (в репозиторий он не попадает — см. «Учебный инцидент» ниже).
   Наружу открыт только **22 (SSH)**; API кластера (`6443`) не публикуем — к нему ходим
   через туннель (§4.4).
3. Пользователь по умолчанию — **`root`** (в отличие от Oracle, где `ubuntu`).

_Бесплатная альтернатива — Oracle Always Free (ARM `A1`), см. «Почему Hetzner»: там
дополнительно собирается VCN и нужен iptables-фикс из §4.4._

### 4.2 Managed Postgres — prod-база (Supabase)

Managed = БД обслуживает провайдер (бэкапы, аптайм, обновления), и она живёт **отдельно
от сервера** — переживёт пересборку кластера.

**Supabase** (https://supabase.com, регистрация через GitHub, free tier): New project →
регион **Европа** (рядом с сервером) → **сохрани сгенерированный пароль БД**. Затем
**Connect → Session pooler** (порт `5432`; IPv4 и работает для миграций — в отличие от
transaction pooler на 6543), подставь пароль и допиши `?sslmode=verify-full`
(проверка сертификата, не просто шифрование — см. Шаг 3):

```
postgresql://postgres.<ref>:<PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=verify-full
```

- ⚠️ Если в пароле есть `@ : / ? # & %` — **percent-encode** их (`@` → `%40`), иначе URL
  распарсится неверно (эти символы в URL — разделители).
- _Neon_ (https://neon.tech) — равноценная альтернатива; у нас его консоль не открылась,
  поэтому взяли Supabase. Смена провайдера = только новый `DATABASE_URL`.

### 4.3 BotFather — prod-токен

`/newbot` → сохрани `TELEGRAM_BOT_TOKEN` (для dev позже заведёшь **отдельного** бота).

### 4.4 Установить k3s и забрать доступ

```bash
ssh root@<IP сервера>
# Лёгкий однонодовый k8s. Отключаем traefik/servicelb — входящий трафик не нужен.
curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--disable traefik --disable servicelb" sh -

k3s kubectl get nodes                # проверка прямо на сервере: нода Ready
cat /etc/rancher/k3s/k3s.yaml        # это kubeconfig; server = https://127.0.0.1:6443

# Подготовка хоста к CD: пользователь deploy, доступ к кластеру, чекаут репозитория,
# скрипт деплоя, CD-ключ (печатается путь), отключение входа по паролю + fail2ban.
curl -fsSL https://raw.githubusercontent.com/Dmitry28/nexo-assist/dev/deploy/setup-server.sh | bash
```

Скрипт печатает **путь** к приватному CD-ключу (его содержимое → `CD_SSH_KEY`) и **значение**
ключа хоста (→ `CD_HOST_KEY`); адрес сервера возьми в консоли провайдера (→ `CD_HOST`).
После этого деплой идёт сам (§5b).

> **Только для Oracle:** их Ubuntu идёт с жёсткими iptables (дефолтный `REJECT`) — поды и
> CoreDNS не стартуют или не видят друг друга. Разреши подсети k3s и сохрани:
> `iptables -I INPUT -s 10.42.0.0/16 -j ACCEPT`, то же для `10.43.0.0/16`, затем
> `netfilter-persistent save`. На Hetzner не нужно.

Работать можно двумя способами:

- **Прямо на VM:** `k3s kubectl ...` (kubectl приходит вместе с k3s) — проще всего.
  Мы заходим как `root`, поэтому `sudo` не нужен; из-под обычного пользователя — `sudo k3s kubectl`.
- **С локальной машины через SSH-туннель** (безопасно, API наружу не открываем):
  сохрани kubeconfig в **отдельный** файл (не затирай существующий `~/.kube/config`),
  оставь `server: https://127.0.0.1:6443`:

  ```bash
  # 1. сохрани содержимое k3s.yaml в ~/.kube/nexo.yaml — туннель сам проверится через него
  # 2. адрес сервера держим вне репозитория (см. «Учебный инцидент» ниже):
  export CD_HOST=nexo                   # + блок `Host nexo` с `HostName <IP>` в ~/.ssh/config
  # (положи эту строку в ~/.zshrc, иначе скрипт остановится с «set CD_HOST…»)

  npm run k8s:tunnel                    # поднимает/чинит туннель и печатает `kubectl get nodes`

  export KUBECONFIG=~/.kube/nexo.yaml   # для дальнейших ручных kubectl-команд
  ```

### 4.5 Образ из GHCR

CI уже пушит `ghcr.io/dmitry28/nexo-assist:sha-<...>` (шаг 5a). По умолчанию пакет
**приватный** → сделай его **public** (GitHub → Packages → package → Settings →
Change visibility). Тогда кластеру не нужен pull-секрет. _(Приватный вариант —

### 4.6 Секреты и деплой

Единственное, чего нет в git и что заводится руками, — Secret с доступами:

```bash
npm run k8s:secrets   # deploy/secrets.sh — скрытый ввод; TELEGRAM_BOT_TOKEN,
                      # DATABASE_URL, SCRAPE_PROXY_URL, SENTRY_DSN

# Корневой CA провайдера руками заводить не нужно — он лежит в репозитории
# (k8s/db-ca-configmap.yaml) и приезжает вместе с `apply -k`.
```

Дальше деплой делает CD: мерж в `dev` → тесты → образ → выкатка (§5b). Тег в
`k8s/kustomization.yaml` уже закоммичен и служит плейсхолдером — `deploy.sh` подставляет
sha деплоя сам, править руками не нужно.

Ручной деплой нужен только если CI недоступен — на сервере:

```bash

```

kubectl logs deploy/nexo-assist -f           # "Bot @... started"

### 4.8 Если что-то не так

- **`Host key verification failed`** в джобе `deploy` — сервер предъявил не тот ключ хоста,
  что записан в `CD_HOST_KEY`. Если ты пересоздавал сервер или перегенерировал ssh-ключи —
  это ожидаемо: возьми новое значение (его печатает `setup-server.sh`) и обнови секрет.
  **Если сервер не трогали — не обновляй секрет «чтобы заработало»**: именно так выглядит
  подмена, от которой эта проверка и стоит. Сначала разберись, почему ключ изменился.
- **`CD_HOST_KEY is missing or malformed`** — секрет не задан или испорчен; деплой остановлен
  **до** подключения, прод не тронут.
- **ImagePullBackOff** — пакет приватный → сделай public (4.5) или заведи pull-секрет.
- **Init:CrashLoopBackOff** (migrate) — проверь `DATABASE_URL` в секрете и логи
  initContainer'а; частая причина — неверный URL/SSL.
- **CrashLoopBackOff** (app) — `kubectl logs`; обычно нет `TELEGRAM_BOT_TOKEN` или
  конфликт `409` (второй поллер на том же токене — не запускай бота ещё где-то).
- **Поды/CoreDNS не стартуют, DNS/pull-таймауты внутри кластера** — почти всегда
  iptables Oracle Ubuntu режет трафик k3s. Разреши подсети и сохрани (см. 4.4):
  `sudo iptables -I INPUT -s 10.42.0.0/16 -j ACCEPT && sudo iptables -I INPUT -s 10.43.0.0/16 -j ACCEPT && sudo netfilter-persistent save`.
- **Oracle "Out of capacity"** — повторяй создание VM / другой регион.
- **`exec format error`** в логах пода — несовпадение архитектуры образа и ноды.
  У нас образ мультиарх (amd64+arm64), так что не должно возникать; если возникло —
  проверь, что CI собрал `arm64` (шаг 5a) и тег образа свежий.

## Первый деплой: что сломалось и чему научило

Деплой прошёл **не с первого раза** — и каждая ошибка была полезной. Порядок реальных
проблем и как их диагностировали (главный навык: **читать логи, а не гадать**):

1. **`Init:CrashLoopBackOff`, в логах `ECONNREFUSED 127.0.0.1:5432`.**
   Причина: Secret создался с **пустыми** значениями (переменные оболочки были очищены
   до `kubectl create secret`; `--from-literal` молча принял пустую строку). Приложение,
   не найдя адрес БД, ушло на дефолт для локальной разработки → localhost.
   **Уроки:** после создания секрета всегда проверяй длины значений; секреты вводи
   интерактивно (`read -rs`), а не в самой команде (иначе попадут в историю оболочки).
2. **`SELF_SIGNED_CERT_IN_CHAIN` при подключении к Supabase.**
   Причина: Supabase использует **свой корневой CA** («Supabase Root 2021 CA»), которого
   нет в списке публичных доверенных у Node — поэтому `sslmode=verify-full` честно
   отказался проверять подлинность.
   **Решение (правильное):** скачали CA **из панели Supabase** (доверенный канал, а не из
   того, что прислал сервер — иначе проверка бессмысленна), положили в ConfigMap
   (сертификат публичный, не секрет; с тех пор он лежит в git как
   [`k8s/db-ca-configmap.yaml`](../k8s/db-ca-configmap.yaml) — руками заводить не нужно),
   смонтировали в оба контейнера и включили
   `NODE_EXTRA_CA_CERTS`. Проверку **не отключали** — наоборот, теперь доверяем только
   сертификатам, выпущенным именно Supabase (строже, чем публичный CA).
3. **Secret обновили — а под работает по-старому.**
   Переменные окружения из Secret подставляются **при старте контейнера**, поэтому
   изменение Secret **не** перезапускает поды: нужен `kubectl rollout restart deployment/...`.
4. **Бот поднялся, но `kufar` вернул `403`.**
   Диагностика: сравнили запрос с локальной машины (Беларусь → `200`) и с сервера
   (ЕС → `403` + страница «Доступ ограничен»). Вывод: **гео-блок источника**, не наш баг.
   `realt.by` из ЕС работает. Решение — прокси с белорусским IP только для kufar
   (см. PRODUCT_PLAN, Фаза 5).
5. **`TLS handshake timeout` у `kubectl`.**
   SSH-туннель «умер», но процесс остался и держал порт → не «отказ соединения», а
   таймаут. Лечится пересозданием туннеля; чтобы не повторялось — запускаем его с
   `ServerAliveInterval` (тогда ssh сам замечает обрыв и завершается).

## Учебный инцидент: адрес сервера попал в публичный репозиторий

**Что случилось:** в `deploy/tunnel.sh` IP сервера был записан как значение по умолчанию
(`4e73a76`, 16.08). Правило «в репозитории нет IP-адресов» к тому моменту было записано уже две
недели как (`e7625b7`, 31.07) — то есть было записано и просто не применено. Адрес остался в истории git.

**Насколько это опасно — по фактам.** Посчитали по журналу:

```bash
journalctl -u ssh --since '7 days ago' | grep -c 'Failed password'   # 40201
journalctl -u ssh --since '7 days ago' | grep -c 'Invalid user'      # 21332
```

**40 201 попытка подбора пароля за 7 дней** — при том, что адрес никто целенаправленно не искал.
Сервера перебирают **все подряд**. Значит секретность адреса — слабая защита, а настоящая держится
на том, **как** пускают внутрь. Публикация адреса добавляет адресности, но дыру сама по себе не создаёт.

**Что нашли при проверке (и это было хуже):**

- `PasswordAuthentication yes` — вход по паролю был **включён**, хотя мы ходим только по ключам;
- `fail2ban` отсутствовал — никто не отсекал перебор.

**Что сделали:**

1. Убрали адрес из репозитория: `tunnel.sh` требует `CD_HOST` (как его задать — §4.4 выше).
   Историю git не переписываем — для публичного репозитория это ломает форки и клоны, а ценность
   адреса низкая; действенная мера — усиление сервера, а не сокрытие. Это осознанный отказ от
   сокрытия: адрес останется публичным навсегда, по-настоящему «убрать» его можно только сменив IP.
2. **Отключили вход по паролю** и **поставили fail2ban** — теперь это шаг 6 в
   `deploy/setup-server.sh`, а не ручная правка, иначе пересоздание сервера вернуло бы дыру.

**Как проверить, что пароль действительно выключен** (важно: недостаточно написать это в конфиг):

```bash
sshd -T | grep -iE 'passwordauthentication|kbdinteractive'   # оба должны быть no
fail2ban-client status sshd                                   # jail активен, видно баны
```

**Почему файл называется `01-hardening.conf`, а не `99-`.** sshd берёт **первое** найденное
значение параметра, а облачные образы кладут свой `50-cloud-init.conf`, который может включить
пароль обратно. Файл с префиксом `01-` читается раньше и побеждает. С `99-` наша настройка на
таком образе оказалась бы **молча бесполезной** — конфиг есть, эффекта нет.

**Роль fail2ban после этого.** Раз пароль отключён, подобрать его нельзя в принципе — fail2ban
здесь уже не то, что «спасает от перебора», а гигиена: разгружает журнал и CPU и прикроет другие
сервисы, если мы их откроем. Не путать эти два уровня местами.

**Урок:** правило, записанное в документе, не выполняется само. И: защищайся от того, что
происходит **всегда** (перебор), а не только от адресных атак; а настройку безопасности
**проверяй по факту** (`sshd -T`), а не по наличию строчки в файле.

**Почему SSH нельзя закрыть по IP:** через него ходит наш CD с GitHub Actions, а у их раннеров
широкие диапазоны адресов. Поэтому упор на ключи + fail2ban, а не на список разрешённых IP.

## Учебный инцидент: проверка «пароль выключен» врала из-за `grep -q`

**Что случилось:** `setup-server.sh` падал с «password auth still on», хотя пароль был выключен.
Та же команда, набранная руками, отрабатывала верно. Расхождение — в `set -o pipefail`.

**Как устроена ловушка.** Строка была такой:

```bash
sshd -T | grep -qx 'passwordauthentication no'
```

`grep -q` завершается **сразу на первом совпадении** — ему больше нечего искать. Но `sshd -T`
в этот момент ещё печатает остальные полсотни строк, и пишет он уже в **закрытую трубу**.
Система убивает его сигналом `SIGPIPE` (код 141). Дальше вступает `pipefail`: он берёт код
самой правой **неуспешной** команды в конвейере. Итог — grep нашёл совпадение (код 0), но
конвейер вернул 141, то есть «не нашёл».

Проверяется одной строкой:

```bash
bash -c 'set -o pipefail; sshd -T | grep -qx "passwordauthentication no"; echo ${PIPESTATUS[*]}'
# 141 0  ← sshd убит, grep успешен
```

**Это гонка, а не гарантия.** Если `sshd -T` успел дописать весь вывод в буфер трубы раньше,
чем `grep -q` завершился, писать в закрытую трубу уже некому — и конвейер вернёт `0 0`.
Поэтому такая ошибка ловится не всегда и на другой машине может «не воспроизводиться».
Тем хуже: баг, который проявляется через раз, живёт в скрипте долго.

**Как починили:** сначала забираем вывод в переменную, потом ищем в ней — трубы нет, убивать
некого:

```bash
SSHD_EFFECTIVE=$(sshd -T)
grep -qx 'passwordauthentication no' <<<"$SSHD_EFFECTIVE" || { ...; exit 1; }
```

**Когда это кусается, а когда нет.** Опасна связка: досрочно выходящая команда (`grep -q`,
`head`) **в конвейере** вместе с `pipefail`. Если grep читает **файл** (`grep -qF ... "$AUTH"`
в том же скрипте) — конвейера нет, проблемы нет. Без `-q` grep дочитывает ввод до конца, и
SIGPIPE не возникает.

**Урок:** `set -euo pipefail` — правильная привычка, но она превращает досрочный выход из
конвейера в ложную ошибку. И более общий: **проверка тоже может быть сломана**. Здесь она
сработала «в безопасную сторону» (ложная тревога, скрипт остановился), но такая же ошибка
с обратным знаком молча пропустила бы дыру.

## Учебный инцидент: таблицы были открыты через публичный API провайдера

**Что случилось:** Supabase прислал алерт «Table publicly accessible — RLS not enabled».

**Почему:** managed-провайдеры поднимают над базой **HTTP-API к таблицам** (у Supabase это
PostgREST) для браузерных приложений. В такой модели защита — **RLS** (Row-Level Security):
правила, определяющие, какие строки видит роль. Наши таблицы создал TypeORM обычными
миграциями, без RLS → значит через этот API их можно было читать и менять.

**Концепт — два разных входа в одну базу.** Наш бот ходит по Postgres-протоколу
(`DATABASE_URL`), а API — по HTTP. Закрытие одного не закрывает другой. Это частая слепая
зона: «база же за паролем» — а рядом открыт второй вход.

**Как закрыли (два независимых рубежа):**

1. **Отключили Data API** в настройках проекта — путь доступа исчез целиком.
2. **Включили RLS** на всех таблицах без разрешающих правил (миграция) — даже если API включат
   обратно, он не получит ни строки. Приложение не пострадало: оно подключается
   **ролью-владельцем** таблиц, а владелец не подпадает под RLS.

**Проверили, а не поверили:** создали в тестовой БД постороннюю роль, выдали ей полные права
на таблицы — и она увидела **0 строк**, а её `DELETE` затронул 0 строк.

**Урок:** у managed-сервисов проверяй, какие ещё интерфейсы к твоим данным они включают
по умолчанию. Advisor'ы провайдера (Supabase → Advisors) стоит просматривать.

## Учебный инцидент: kubeconfig попал в переписку

**Что случилось:** при настройке k3s админский `kubeconfig` (в нём приватный ключ с
правами `cluster-admin`) был вставлен в чат — то есть «засветился».

**Чем опасно:** `cluster-admin` = полный контроль над кластером (запуск любых
контейнеров, чтение всех секретов, фактически root на сервере) — **если** есть сетевой
доступ к API кластера (порт `6443`).

**Как закрыли:**

1. **Firewall** (входящий только SSH 22) → порт `6443` недоступен из интернета.
2. **Переустановили k3s** → новые сертификаты, старый ключ стал недействителен.

Оба действия — **до** добавления секретов (токен/БД), так что внутри кластера красть
было нечего.

**Урок:** секреты / kubeconfig / токены **никогда** не вставляем в чат, логи, скриншоты;
API кластера не выставляем в интернет; при утечке — ротация ключа + ограничение доступа.

## Скрипты в `deploy/` (рутина одной командой)

| Скрипт                                         | Когда нужен                                                                                                     |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| [`tunnel.sh`](../deploy/tunnel.sh)             | `kubectl` с ноутбука не достучался (`connection refused` / `TLS handshake timeout`) — переподнимает SSH-туннель |
| [`secrets.sh`](../deploy/secrets.sh)           | завести/обновить секреты в кластере (скрытый ввод, значения не попадают в историю)                              |
| [`setup-server.sh`](../deploy/setup-server.sh) | подготовить новый хост под CD (переезд)                                                                         |
| [`deploy.sh`](../deploy/deploy.sh)             | выкатить коммит; обычно вызывается автоматически из CI                                                          |

**Почему они в репозитории, а не «в голове»:** операция, которую повторяешь руками, должна быть
записана — иначе при переезде или сбое её приходится вспоминать. Плюс в скриптах зафиксированы
неочевидные детали: мёртвый туннель держит порт (отсюда `pkill` перед подъёмом), а `kubectl` без
явного kubeconfig может уехать **в чужой кластер** — оба скрипта указывают наш файл явно.

### Где владелец хранит секреты

Секреты нужны в двух местах: в кластере (оттуда их читает приложение) и **у владельца** —
иначе после пересборки кластера восстанавливать будет неоткуда.

**Менеджер паролей** (Bitwarden бесплатен и имеет CLI — потом сможем брать значения оттуда
автоматически). Одна запись `nexo-assist — prod` со скрытыми полями:

| Поле                 | Где перевыпустить, если утёк                             |
| -------------------- | -------------------------------------------------------- |
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/mybots` → бот → API Token → **Revoke**    |
| `DATABASE_URL`       | Supabase → Settings → Database (сброс пароля там же)     |
| `SCRAPE_PROXY_URL`   | пароль на прокси-хосте: `/root/proxy/pass`               |
| `SENTRY_DSN`         | Sentry → Settings → Client Keys → новый ключ, старый off |

**Колонка «как перевыпустить» — половина ценности записи:** утечка тогда не паника, а
процедура на минуту. Все четыре значения отзываемы, поэтому их потеря — неудобство, а не
катастрофа.

Отдельно положи туда же **приватный SSH-ключ** (`~/.ssh/nexo-assist`): его потеря отрезает
доступ к серверам (восстановимо через консоль провайдера, но болезненно). `~/.kube/*.yaml`
бэкапить не нужно — он лежит на сервере (`/etc/rancher/k3s/k3s.yaml`).

⚠️ **Секреты живут только в кластере.** Держи значения в менеджере паролей: после пересборки
кластера `secrets.sh` восстановит их одной командой. Правильное решение (зашифрованные секреты
в git через SOPS+age) запланировано — см. PRODUCT_PLAN.

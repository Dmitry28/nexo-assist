# Product Plan — Listing Watch Bot

Дорожная карта: превращаем прототип `land-scraper` в многопользовательский
сервис на скелете **nexo-assist** (NestJS 11). Логику парсинга портируем из
land-scraper с рефакторингом. Развиваем по фазам — от простого локального к
распределённому. Как продукт работает — в [PRODUCT.md](PRODUCT.md).

---

## 1. Принципы

- По фазам: от простого локального к сложному распределённому.
- Best practices: Docker/k8s, секреты, observability (otel/prometheus/pino в
  скелете), миграции БД, тесты на каждый адаптер.
- Каждая фаза: на входе детально изучаем и обсуждаем варианты; этот документ —
  только высокоуровневый каркас.

### Фаза 2 — Плагинная архитектура

Делаем под-шагами:

- **2.1 — сделано:** `SourceAdapter` + `SourceRegistry`, kufar переехал в `sources/kufar/`
  адаптер; ядро (`WatchService`/scheduler) ходит через реестр; контракт пока lean
  (`id`/`matches`/`fetch`); unit-тесты на адаптер с фикстурами.
- **2.2 — сделано:** realt-адаптер (2-й источник) + матчинг/регистрация.
- **2.3 — сделано:** пагинация с лимитом страниц (page-cap), newest-first.
  Стоп-на-виденных (ранний выход) — опциональная оптимизация позже.
- **2.4 — нормализация URL сделано:** `normalizeUrl` (host/www, отбрасывает волатильные
  и `utm_*` params, сортирует остальные, trailing slash) + колонка `normalizedUrl`,
  уникальный индекс `(userId, normalizedUrl)`, дедуп в `add()`.
- **2.4 — price и removed сделаны (2026-10-13).** Таблицу `listings`/price-history ждать
  не стали: изменению цены нужна только последняя цена, а она легла снимком (`snapshot jsonb`) в
  строку `seen_listings` — по подписке, без новой таблицы. Общая таблица и история нужны fan-out и
  аналитике (Фазы 3/8) — заводим, когда появится их потребитель. Правило цены — из прототипа
  (`subscriptions/price-change.ts`): две валюты — обе в одну сторону на ≥ 2 %, одна — ≥ 2 %;
  сравниваем только числа (зарплата «не указана → 1500» — не изменение цены); пропавшая цена — не
  изменение (страница не показала её — чаще, чем продавец убрал), появившаяся — изменение. Снимок
  при подписке не пишется (базовая линия может не открывать лоты — цены были бы неполные), первый
  опрос заполняет его молча. Больше половины объявлений разом — не продавцы, а правка парсера или
  сайта: запоминаем молча, предупреждение в Sentry. Повторно встреченное объявление
  обновляется целиком (второе правило ниже). Removed — только у источника с `reportsRemoved`
  (фиксированные прайсы: ghb, prometr, gridom; не архив аукционов и не поиск — там уход со страницы
  не продажа) и только при `complete`, без `capped`, на непустой странице; больше половины списка
  разом — не снимаем, предупреждение (пороги и почему — у `isMass` в `watch.service.ts`). Правила из прототипа, первое оплачено инцидентом:
  - **«Пропало из выдачи» ≠ «снято».** Снятие по отсутствию допустимо, только если выдача
    целиком вошла в окно (`complete` и последняя страница без продолжения). Пустой или частичный
    fetch не снимает никогда: у прототипа Cloudflare вернул 0 — и 45 машин разом ушли в
    «снятые».
  - **Повторно встреченное объявление обновлять целиком**, сохраняя служебные поля. Иначе правки
    продавца и исправления парсера никогда не доходят до хранилища.

### Фаза 3 — БД и мультипользовательность

Цель: заменить in-memory на Postgres и вынести юзеров в отдельную сущность.
Минимально: без `listings`/price-history и без дедупа-по-URL — это отдельный
шаг позже. Делаем под-шагами.

**Решения фазы:**

- Один `DATABASE_URL`. Локально — Docker; прод — managed Postgres через pooled-endpoint,
  SSL обязателен, учесть дроп idle-коннектов. На момент фазы выбран был Neon; он не открылся,
  прод уехал на Supabase — см. «Решения».
- Только генерируемые миграции; `synchronize: false` всегда. Отдельный
  `data-source.ts` для CLI (не переиспользуем `TypeOrmModule.forRootAsync`).
- `source` — `varchar`, не PG-enum (новый источник не должен требовать миграцию типа).
- UUID PK для `users`/`subscriptions` (уже так); `seen_listings` — составной PK
  `(subscription_id, external_id)` без суррогатного id (он же и индекс проверки).
  Timestamps; `baselinedAt` nullable. FK — `ON DELETE CASCADE`.
- Тесты: юнит — лёгкий in-memory fake репозитория (быстро, без БД); e2e/интеграция —
  реальный Postgres из docker-compose (сервис в CI).

**3.1 — Инфра БД — сделано.** 3.1a: Postgres в `docker-compose.yml` (+ healthcheck)
и скрипты `db:up/down/reset`. 3.1b: зависимости (`@nestjs/typeorm typeorm pg`),
`DATABASE_URL` в env.validation + configuration + `.env.example`,
`TypeOrmModule.forRootAsync` (inject `AppConfig`, `autoLoadEntities`,
`synchronize:false`, SSL для не-локальных), readiness-проба `db.pingCheck`, сервис
Postgres в CI. (k8s Secret для `DATABASE_URL` — в Фазе 5, деплой.)

**3.2 — Схема + первая миграция — сделано.** Сущности `Subscription` (uuid PK,
`telegramUserId`, source, url, createdAt, `baselinedAt`) и `SeenListing` — составной

**Решено 2026-09-11: карточка на объявление, всегда — с фото и картой.** Вопрос стоял так: у

карту и полную карточку бесплатно. Цена решения: подписи деталей — русский текст, который
производит адаптер, то есть презентация слегка протекает в слой источников (учесть на шаге i18n,

### Фаза 5.7 — Добрать из прототипа остаток — **после 5.6**

Решено 2026-09-14. Сплошной обход прототипа делался 2026-09-11 (§5, «просмотрены все 127 файлов
вне модулей-источников»). Сегодня он повторён независимо — не сверяясь сначала с §5 — и
записанное там подтвердилось: расхождений «записано неверно» нет. Остаток, которого в §5 не
было, собран здесь. Он невелик, поэтому отдельной большой фазы не заводим: пункты делаются при
ближайшем касании соответствующего кода, кроме лестницы — она приезжает с первым защищённым
источником в 5.6.

- **Три разных исхода у внешней загрузки, а не один «не смог»:** тариф не умеет такой запрос,
  квота исчерпана, байпас сорвался. Путать дорого: у прототипа ScraperAPI на бесплатном тарифе
  отвечал 403 на **каждый** анти-бот-запрос, и цепочка переспрашивала его в каждом фиде каждого
  прогона. Лечится памятью на прогон: ступень, отказавшая по тарифу или по квоте, до конца
  прогона больше не вызывается.
- **Перемежающийся отказ — не мёртвая ссылка.** У ZenRows 422 задокументирован как сорвавшийся
  байпас: тот же фид четыре прогона подряд отдавал 422, на пятом — 690 КБ с теми же
  параметрами. Перед переходом на следующую ступень дать пару ретраев с паузой, иначе такие
  источники будут списываться в «обнови ссылку».
- **404 на последней странице — штатный конец пагинации, а не сбой.** У одного источника
  прототипа ровно пять страниц, и шестая всегда 404. У нас любой не-`ok` — это
  `SourceUnavailableError`, то есть первый же такой источник начнёт ежедневно поднимать ложную
  тревогу. Нужен `NOTE` и способ для адаптера объявить это ожиданием.
- **Правила для HTML-источников** (у нас пока оба на `__NEXT_DATA__`, но 5.6 это изменит):
  якорь парсера — путь ссылки (`a[href*="/lot/"]`), а не CSS-класс, иначе ребрендинг вёрстки
  ломает адаптер; и имя класса встречается **внутри** `<style>`, поэтому поиск по голому имени
  даёт фантомные строки — сплитить по открывающему тегу и пинить тестом.
- **`_DOC.md` рядом с адаптером** с секцией «пришло 0 объявлений — проверь вот это». В
  прототипе пять таких файлов, и окупаются они ровно в момент поломки. Завести вместе с первым
  адаптером Фазы 5.6, пока их мало.
- **Cadence guard как отдельное понятие.** Единый `WATCH_CRON` — не та ручка для источника с
  лимитом запросов: у прототипа для такого источника свой минимальный интервал (47 часов).
  Сейчас не нужен; знать заранее дешевле, чем узнать по счёту.
- **Нормализация для кросс-сорс дедупа**, если до него дойдёт: снять кавычки, хвостовую скобку
  и организационно-правовую форму (`ООО`, `ЧУП`, …) — иначе одно объявление на двух площадках
  не склеится.
- **Потеря `seen_listings` выглядит как тихий рынок, а не как инцидент.** У прототипа порча
  файлов снапшота разом ре-базлайнила 34 фида, и заметили постфактум. Наш эквивалент —
  `baselinedAt`: подписка с пустым seen-множеством молча начинает с чистого листа. Нужен хотя бы
  алерт владельцу на массовое обнуление.
- **Порог покрытия тестами** (у прототипа branches 50 / lines 70 в `package.json`). У нас
  `test:cov` в CI без порога. Решение владельца, заводим ли.

**Наш прокси — бесплатная ступень лестницы** (решение владельца 2026-10-07): обычный запрос →
наш прокси (`SCRAPE_PROXY_URL`, Oracle) → платные. Ожидание скромное: IP дата-центра в ЕС, так что
Cloudflare (bamper, bid.cars) и WAF (av.by) его вероятно не пропустят, а idriver пускает только
белорусские IP — но проба бесплатна, и каждый сайт, который через него проходит, экономит
платную квоту. Проверить с сервера (прокси открыт только ему) до подключения платных.

**Платная ступень загрузки — решение с арифметикой.** Механику лестницы берём, она полезна и
бесплатна: порядок ступеней, предикат «это та страница, а не заглушка», первая настоящая ошибка
наружу, локальный браузер второй ступенью. А вот платного провайдера заводим **не про запас, а
под конкретный источник** — потому что счёт не сходится. **Уточнено 2026-10-05:** живых
бесплатных провайдеров у прототипа три, все с ежемесячным обновлением: ZenRows (5000 кредитов,
защищённая страница — 10 без рендера и 25 с рендером, то есть ~500 или ~200 страниц), Scrape.do
(1000, 10/25 — ~100 или ~40 страниц) и добавленный 2026-09-29 ScrapeOps (1000, 10/25, оплачиваются
только ответы 200/404 — сорвавшийся байпас бесплатен). Итого **~280–700 защищённых страниц в
месяц, 9–23 в сутки**, в зависимости от того, нужен ли сайту рендер. Один прогон подписки — до
5 страниц, то есть это несколько подписок к защищённым источникам в сутки, а не сервис для
многих пользователей. Поэтому вместе с первым таким источником решается и вопрос «что делаем,
когда страницы закончились»: лимит на подписки к защищённым источникам или отказ от них.
**Решено 2026-10-13 (шаг 4а):** лимит в кредитах, одно правило для всех — `DAILY_CREDIT_BUDGET` =
200 в сутки, ровно бесплатные ZenRows + Scrape.do (6000 в месяц / 30); подписка стоит худшую цену
своего опроса — 10 кредитов, 25 с рендером (`paidPoll`), один запрос на опрос. ScrapeOps (ещё 1000) в сумму не входит: он — запас на базовые линии и `/check`, которые опрашивают сверх
ежедневного прогона, и последняя ступень (2 мин своих ретраев — ему достаётся время, только когда
ступени до него быстро отказали). Бесплатные белорусские прокси (ступень перед платными) делают
реальный расход ниже худшего. ScrapFly — разовый запас, вне суммы.
**Уточнено 2026-10-15 (bid.cars для компании, только бесплатно):** бюджетов два, по наборам
провайдеров, которые не пересекаются (`poolOf`): сайты со страной — ZenRows, Scrape.do, ScrapeOps,
ScrapFly, бюджет 200 как выше; сайты без страны — только ScrapingAnt и ScraperAPI
(bid.cars с 2026-10-19 не на лестнице — Copart+IAAI, бэклог «bid.cars бесплатно и массово»),
бюджет 300 = (10000 ScrapingAnt − ~1000 запаса на базовые линии и `/check`) / 30, страница 10
кредитов с браузером (по прайсу), **1 без браузера** (замер 2026-10-20, `ant-credits-cost` на POST
Copart; ScraperAPI — тоже 1, рендер ~21 из своих 1000 — запас вне суммы). Опрос Copart и bid.cars — 6
(`paidPoll`: 500 лотов Copart = 6 страниц из‑за повторов), то есть ~50 разных поисков на бот. Раньше bid.cars проваливался после
них в ZenRows и тратил чужой бюджет; теперь ScrapingAnt получает всю минуту вместо 30 с. Считаются
уникальные поиски, а не подписки: прогон скачивает одинаковый поиск один раз (`SharedFetches`) —
подписка на поиск, который уже кто-то смотрит, бесплатна. Сводка источника по прогону тоже
считает поиск один раз, иначе один мёртвый поиск у трёх пользователей читался бы как падение сайта.

Оттуда же две измеренные ловушки по флагам, чтобы не платить за них второй раз: рендер
страницы **не входит** в анти-бот-тариф и биллится отдельно — включённый вместе с ним, он
переводит каждый вызов из 10-кредитной корзины в 25-кредитную (прототип так сжёг почти месячный
тариф впустую); и наоборот, после рендера нужна явная пауза — без неё источник отдавал 254 КБ и
**ноль** лотов, с десятисекундной паузой — 764 КБ и 53 лота.

Эксплуатационные уроки лестницы — из третьего прохода 2026-10-05 (по файлам с вердиктом на
каждый, все файлы рабочей копии прототипа, кроме `data/`, сгенерированных хуков husky, настроек
IDE и lock-файла, плюс все его коммиты после 2026-09-10 — прототип менялся после прошлых
обходов). Прошлые выводы подтвердились; остальное новое разнесено по местам: 2.4, 3.4, 5.6,
Фаза 7, бэклог и §5. Взять вместе с лестницей:

- **Платная ступень — только в проде** (или отдельный аккаунт для локалки). У прототипа dev и
  prod делили ключи: dev-прогон 28.09 сжёг ScrapFly, и 29.09 прод упал на всех фидах.
  **Решение владельца 2026-10-14:** локально те же ключи — тестировать их как-то надо; правило —
  разовые проверки, без активных локальных подписок на защищённые сайты (`.env.example`).
- **Таймаут ступени > её рендер + пауза.** 30 с обрезали ZenRows — и наш `FETCH_TIMEOUT_MS`
  (`http.ts`) ровно 30 с. ScrapeOps сам ретраит цель до
  2 минут — ему нужен таймаут ≥150 с и строго один запрос за раз (429 = лимит параллельности);
  это 5 страниц ≈ 12,5 мин на подписку. Сторож прогона `POLL_STUCK_AFTER_MS` (6 ч, Фаза 5.5)
  посчитан из ~3,5 мин на подписку и сработает уже на ~28 таких подписках — пересчитать.
- **Цену вызова Scrape.do берём из ответа** (`scrape.do-request-cost`): он сам включает
  резидентный прокси и рендер там, где они нужны, и свой расчёт врёт.
- **ScrapingAnt не умеет гео-Беларусь** (`proxy_country=by`), а гео-блок (403 «запрос
  заблокирован» с IP) выглядит как несработавший challenge — различать по телу ответа.
- **После challenge — фиксированная пауза, а не `waitForSelector`:** перезагрузка страницы рушит
  контекст. JSON-API, открытый браузером, приходит внутри `<pre>` с экранированием — второй
  потребитель `decodeHtmlEntities` (§5).
- **Локальный браузер в нашем рантайме.** В образе (`node:24-alpine`) браузера нет: нужен
  системный Chromium с зависимостями, `PUPPETEER_SKIP_DOWNLOAD=true` в CI и сборке (иначе
  каждый `npm ci` качает Chrome), флаги Chromium `--no-sandbox`, `--disable-dev-shm-usage` и
  `--disable-blink-features=AutomationControlled`, ленивый запуск с пересозданием упавшего
  браузера. Лимит пода 512Mi для браузера, вероятно, мал — **не измерено**, замерить до деплоя.
  Записать в PRODUCT_TECH/DEPLOY вместе с изменением образа.
- **Операционный раздел в DEPLOY.md** при подключении провайдера: даты сброса квот (ZenRows — 3-е
  число, Scrape.do — около 16-го), проверка остатка (Scrape.do `/info`, ZenRows
  `/v1/subscriptions/self/details`) и таблица кодов по провайдерам — смысл у каждого свой: у ScrapeOps
  401 — кончилась квота, 403 — неверный ключ; у Scrape.do 401 «rejected the token» на деле значит
  «кончились кредиты» (`/info` → `IsActive:false`); 423 у ScrapingAnt — его обнаружил сайт, а не
  квота.

### Фаза 6 — Неподдерживаемая ссылка → GitHub Issue → LLM-адаптер — **заявка сделана 2026-10-20**

Превращает «мы это не поддерживаем» в заявку: раньше незнакомая ссылка была тупиком и для
пользователя, и для нас (мы даже не узнавали, чего просили).

- **Сделано 2026-10-20 (решение владельца: «пришла ссылка, которую не умеем, — issue, я запускаю
  LLM, она добавляет парсер»).** Ссылка с неизвестного сайта сразу, без кнопки и вопросов,
  становится GitHub issue «Source request: <сайт>» с меткой `source-request`
  (`SourceRequestsService`): один issue на сайт, следующие ссылки — комментариями, до 5 образцов;
  не больше 10 новых issue и 50 ссылок в сутки (боту пишет кто угодно); закрытый владельцем issue = отказ, сайт больше не заявляется. Пользователю — «передал заявку».
  **Ссылка публикуется целиком**, кроме логина/пароля в ней и `#…`, и как код — чтобы `@имя` не пинговало людей на GitHub (решение владельца: LLM нужны фильтры поиска; репозиторий
  публичный — случайно присланное личное владелец закрывает руками), **заявитель — нет**
  (ни id, ни имени: репозиторий публичный — отменяет «telegram_id заявителя» из исходного плана).
  Токен — `GITHUB_ISSUES_TOKEN`, без него ссылка только отклоняется.
- Отличать ссылку на поиск от ссылки на конкретное объявление. **Решено иначе 2026-10-19
  (владелец):** ссылка на объявление — не ошибка, а слежка за ним (Фаза 7, «Избранное»); отказ
  «пришлите поиск» остаётся только сайтам, где это ещё не сделано.
- TODO: распознавать «голые» домены без `http://` (сейчас — «пришлите ссылку»).
- **Заявителю сообщаем, когда сайт добавлен** (2026-10-20): связь «кто просил — какая ссылка»
  хранится у нас в БД (`source_requests`), не в публичном issue; суточный прогон сверяет ссылки с
  источниками и пишет «✅ Хорошая новость: теперь я умею следить за …» один раз, затем удаляет заявку. Без связки с
  номером issue: сайт считается добавленным, когда его ссылку читает источник.

### Фаза 7 — UX-апгрейды

  только свои подписки). Выбор «сдаться и алертить» держится на том, что окно крошечное: слот
  берут только те, кто пишет `seen` (сам прогон и `/check`, а тот в проде только у владельца).
  **Уточнено 2026-09-07:** кнопка «Показать текущие» ходит в источник живьём, но со слотом
  не взаимодействовала вовсе. Напрашивавшаяся правка — закрыть её тем же слотом, то есть
  _занимать_ его, — сломала бы эту посылку: `runDaily` отменяет прогон, когда слот занят, так
  что любой пользователь одним нажатием отменял бы общий прогон. Поэтому кнопка слот только
  _подсматривает_. Правило теперь явное — слот держат исключительно опросы, пишущие `seen`;
  любой новый читающий путь обязан подсматривать.
  Дешёвая страховка — одна повторная попытка через минуту. Решать, когда крон станет чаще
  суточного.
- **`/help` обещает «раз в сутки», хотя частота настраивается.** `WATCH_CRON` — переменная;
  в день, когда прогон станет чаще, текст станет враньём. Подставлять расписание в текст пока
  не стоит (крон в человекочитаемый вид не переводится в одну строку) — поправить вместе с
  повышением частоты.
- **Тест «все команды меню есть в справке» не может упасть.** Справка сама строится из
  `BOT_COMMANDS`, поэтому проверка воспроизводит собственное ожидание. Стережёт только будущий
  захардкоженный список. Заменить на проверку отрендеренной строки при следующем касании.
- **«Сигнал жизни» подтверждает только живой процесс.** Если long-polling или суточный прогон
  встанут, а HTTP-сервер останется жив, сторож будет спокоен. `PRODUCT_TECH.md` описывает это
  честно («приложение умерло целиком»), но дыра есть. Закрывается второй проверкой с периодом
  суток, куда пингует сам прогон, — делать вместе с повышением частоты проверок.
- **`import-x/no-cycle` не работает.** Молчит и на реальном цикле, и на тривиальном из двух
  файлов в изолированном конфиге — дело в связке eslint 10 / eslint-plugin-import-x, а не в
  наших настройках. Правило оставлено (сработает после бампа плагина); пока его роль выполняет
  `src/__tests__/di-wiring.spec.ts` — там же разобран сам инцидент. Разобраться при ближайшем
  обновлении линтерных зависимостей.
- **Опрос «по требованию» ничем не ограничен по частоте.** Слот кнопка «Показать текущие»
  теперь уважает (закрыто 2026-09-07), но ни у неё, ни у baseline при подписке нет ни счётчика,
  ни пауз: сколько раз человек нажал — столько запросов ушло в источник. Ограничитель один —
  скорость пальца. Нужен троттлинг на пользователя; делать вместе с кнопкой «Показать ещё»
  (Фаза 7).
- **Sentry ловит не всё, что глушится.** `notifyAdmin`, dead-link-нотис и «Admin alert failed»
  логируются `logger.warn` и наружу не уходят. Если владелец перестанет получать алерты, он об
  этом узнает только по тишине — то есть никогда.

  но лечится курсором/батчами, когда прогон начнёт упираться в память.

  следующего вызова (самолечится, но несогласованно с sibling-методом).
- **Мигающий e2e: `getSeen refreshes seenAt` [M].** Наблюдался один провал из четырёх прогонов
  подряд (2026-09-06, локально): `after` оказался на 44 мс **раньше** `before`
  (`test/watch.e2e-spec.ts` ~:173). Что уже исключено измерением, а не догадкой: это не
  регрессия правок (три последующих прогона зелёные, логика `getSeen`/`markSeen` не менялась) и
  не расхождение часов — `clock_timestamp()` Postgres против хоста даёт ±2 мс на пяти замерах.
  Остаётся подозрение на смешение источников времени: строка вставляется без `seenAt` (колонка
  имеет `DEFAULT now()`, см. `InitSchema`), а обновляется JS-значением `new Date()` из
  `getSeen`. Прямой зонд упёрся во внешний ключ (нужна настоящая подписка), поэтому механизм не
  подтверждён — чинить вслепую нельзя ([debugging.md](llm/rules/debugging.md) § Iron Law).
  Важно: смешение источников времени — свойство **продакшена**, а не только теста. Вставка
  берёт `DEFAULT now()` (часы БД), а `getSeen` пишет `new Date()` (часы приложения), то есть
  сортировка «оставить N новейших» в prune сравнивает показания двух часов и на живых
  данных. При заметном расхождении prune может удалить строку, которая ещё в окне, и
  объявление уйдёт повторно как новое. Пока не исправлено, тест оставлен как есть — без
  skip и без допуска, то есть он может покрасить CI.
  Следующий шаг: воспроизвести в цикле с реальной подпиской и писать `seenAt` одним
  источником времени (`now()` на стороне БД в обоих путях).
- **`WATCH_CRON`: настоящая cron-валидация** в env-схеме (сейчас только «5 полей»;
  мусор валит бут позже, в конструкторе CronJob).

Читать надо не только сам модуль: причины решений лежат в `_DOC.md` рядом с ним (шесть штук),

живых прогонов, 1894 объявления kufar/realt ровно с нашим набором полей, то есть бесплатный

Уже портировано: источники прототипа (`sources.ts`) + нормализация цен (BYN/USD); фикстуры в `__tests__`.

Привнести позже:

- **Богатая карточка: поля, фото, точка на карте, устойчивая отправка** — Фаза 5.5 выше.
- **kufar: перейти на официальный search-API** (`api.kufar.by`, как в land-scraper)
  вместо HTML — легче и стабильнее.
- **Лестница загрузки для защищённых сайтов** (`common/scraping/`, 10 файлов кода): обычный запрос →
  локальный браузер (`rebrowser-puppeteer`) → цепочка платных провайдеров, причём каждый
  источник объявляет только те ступени, которые для него измеримо работают (браузер не пробивает

  ступень считается успешной только если тело прошло предикат «это та страница, а не заглушка», и
  наружу надо отдавать **первую настоящую** ошибку цепочки, а не последнюю — три дня простоя
  bamper списывали на «закончилась квота», хотя причина была в 422 от другого провайдера двумя
  звеньями раньше. Нам это понадобится с первым источником за Cloudflare (bid-cars); платные
  ступени противоречат правилу «только бесплатные тарифы», так что из лестницы возьмём
  бесплатные — предикат пригодности и локальный браузер.
  **Насколько бесплатная ставка обоснована — измерено, ответ «зависит от сайта»:** с одних и тех
  же адресов дата-центра bid.cars отдавал 51 объявление, а bamper.by отказывал наотрез. Для нашей
  цели путь работает, но для следующего сайта может не сработать — и тогда бесплатный вариант
  остаётся один: выход с другого адреса, а не патчи браузера. И предикат пригодности там строже,
  чем «не заглушка»: на страницах проданных лотов их браузер проходил challenge и **не рисовал ни
  одного лота**, тогда как провайдер с обычного адреса отдавал все 50 — «challenge пройден, список
  пуст» тоже не доказательство пустого поиска.
- **Измеренная экономика бесплатных тарифов провайдеров** — шапка `common/scraping/scraping.module.ts`.
  Если для источника за Cloudflare всё-таки понадобится провайдер, этот комментарий экономит день
  исследования: порядок цепочки там выстроен по стоимости, а не по возможностям, и каждая цифра
  измерена живьём. Коротко: ScraperAPI считает запросы (1000/мес), но на бесплатном тарифе не

- **`list_time` у kufar — не время последнего изменения.** Правка цены его не двигает (из 56
  изменений цены ни одно не имело `list_time` свежее 48 часов; у realt `updatedAt` — двигает),
  поэтому изменения ищем полным дифом по снимку, а не окном по времени; смена валюты — тоже
  изменение цены (103 500 USD → 207 000 BYN). Мы показываем его в карточке как признак свежести, нигде не оговорив
  этого. Оттуда же измерения, обосновывающие правило смены цены: дрейф курса даёт одинаковую

  применяется ежедневно, и «старый сегодня» штамп мог быть свежим в день прогона.

  в потолок страниц раньше неё. У нас тот же эффект возникнет сам собой, и он скорее правильный
  — но нигде не обсуждён.
- **Lookback-окно** как оптимизация пагинации (вместо только page-cap).

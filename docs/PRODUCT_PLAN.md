# Product Plan — Listing Watch Bot

Дорожная карта: превращаем прототип `land-scraper` в многопользовательский
сервис на скелете **nexo-assist** (NestJS 11). Логику парсинга портируем из
land-scraper с рефакторингом. Развиваем по фазам — от простого локального к
распределённому. Как продукт работает — в [PRODUCT.md](PRODUCT.md).

---

## 1. Принципы

- По фазам: от простого локального к сложному распределённому.
- Best practices: Docker/k8s, секреты, observability (otel/prometheus/pino в
  скелете), миграции БД, тесты на каждый адаптер.
- Каждая фаза: на входе детально изучаем и обсуждаем варианты; этот документ —
  только высокоуровневый каркас.

## 3. Фазы

### Релиз бете — что должно быть готово (текущая цель)

и свои бэкапы БД. Последний пункт закрыт 2026-09-05: у провайдера бэкапов на free-тарифе нет
(проверено в панели), поэтому ночной `pg_dump` из кластера — см. [PRODUCT_TECH.md](PRODUCT_TECH.md).

Найденное по дороге, но не блокирующее, — в бэклоге ниже или как `TODO` в коде.

### Фаза 3 — БД и мультипользовательность

Цель: заменить in-memory на Postgres и вынести юзеров в отдельную сущность.
Минимально: без `listings`/price-history и без дедупа-по-URL — это отдельный
шаг позже. Делаем под-шагами.

**Решения фазы:**

- Один `DATABASE_URL`. Локально — Docker; прод — managed Postgres через pooled-endpoint,
  SSL обязателен, учесть дроп idle-коннектов. На момент фазы выбран был Neon; он не открылся,
  прод уехал на Supabase — см. «Решения».
- Только генерируемые миграции; `synchronize: false` всегда. Отдельный
  `data-source.ts` для CLI (не переиспользуем `TypeOrmModule.forRootAsync`).
- `source` — `varchar`, не PG-enum (новый источник не должен требовать миграцию типа).
- UUID PK для `users`/`subscriptions` (уже так); `seen_listings` — составной PK
  `(subscription_id, external_id)` без суррогатного id (он же и индекс проверки).
  Timestamps; `baselinedAt` nullable. FK — `ON DELETE CASCADE`.
- Тесты: юнит — лёгкий in-memory fake репозитория (быстро, без БД); e2e/интеграция —
  реальный Postgres из docker-compose (сервис в CI).

**3.1 — Инфра БД — сделано.** 3.1a: Postgres в `docker-compose.yml` (+ healthcheck)
и скрипты `db:up/down/reset`. 3.1b: зависимости (`@nestjs/typeorm typeorm pg`),
`DATABASE_URL` в env.validation + configuration + `.env.example`,
`TypeOrmModule.forRootAsync` (inject `AppConfig`, `autoLoadEntities`,
`synchronize:false`, SSL для не-локальных), readiness-проба `db.pingCheck`, сервис
Postgres в CI. (k8s Secret для `DATABASE_URL` — в Фазе 5, деплой.)

**3.2 — Схема + первая миграция — сделано.** Сущности `Subscription` (uuid PK,
`telegramUserId`, source, url, createdAt, `baselinedAt`) и `SeenListing` — составной
PK `(subscriptionId, externalId)` (он же индекс проверки «видели/нет»), `seenAt`, FK
→ subscription `ON DELETE CASCADE`. `data-source.ts` (CLI) + скрипты
`migration:generate|run|revert|show` (ts-node/tsconfig-paths) + первая миграция
`InitSchema`. `User` + FK `subscription → user` + `forFeature` — в 3.3 (вместе с их
первым потребителем).

**3.3 — Перенос сервисов на БД (async) — сделано.** `SubscriptionsService` через
`@InjectRepository` + `TypeOrmModule.forFeature`; методы стали `async` → await в
`WatchService`, `telegram.handlers`, `watch.scheduler`. `getSeen` — запрос по кандидатам
прогона (`external_id = ANY(ids)`), не загрузка всего сета. `baseline` (seed +
mark-baselined) — в одной транзакции (`seedBaseline`). Удаление подписки каскадит
`seen` (FK). Тесты: слой данных → интеграционный на реальном Postgres (`test/`), юниты
`handlers`/`scheduler` — на моках коллабораторов. Ключ пока — `telegramUserId`.

**3.3b — Таблица `User` + профиль — сделано.** `User`-сущность (аккаунт: `telegramId`
unique — первая identity; username, имя, язык; веб-авторизация позже расширяет тот же
ряд); `Subscription` → `user` (eager, FK `ON DELETE CASCADE`), `telegramUserId` убран.
Upsert профиля при подписке (`ctx.from` → `users`). Миграция `AddUsers`. Ключ снаружи
остаётся telegram-id (сервис резолвит в user). Профиль пока не читается — собираем
заранее (при подписке `ctx.from` есть, потом не восстановить).

**3.4 — Чистка `seen` по окну — сделано.** Бот смотрит только первые несколько страниц
поиска (page-cap ≈ 150 самых свежих); всё, что уехало дальше, он больше не запрашивает —
значит и «новым» показаться не может. Поэтому храним только последние `N` виденных id на
подписку (`MAX_SEEN_PER_SUBSCRIPTION=300`, с запасом к page-cap), старые удаляем прунингом
после каждой вставки. Таблица на подписку ограничена навсегда, без риска повторно прислать
старое.

**3.5 — Лимиты / анти-абьюз — сделано.** Max подписок на юзера
(`MAX_SUBSCRIPTIONS_PER_USER=50`, проверка в `add`) + запрет дублей по точному URL;
дружелюбные сообщения в боте (лимит / «уже отслеживаешь»). Полная уникальность
`(user_id, normalized_url)` + DB-констрейнт — со шагом нормализации URL (Фаза 2.4).

**3.6 (опц.) — In-run fetch-кэш.** Несколько подписок на один URL в одном прогоне →
один fetch (Map на прогон). Дешёвый предшественник дедупа; можно перенести в Фазу 4.

**Отдельным шагом (позже, вне Фазы 3):** дедуп-по-URL (один скрейп на нормализованный
URL → fan-out) и вместе с ним `listings` + **снимки цен** (price history) — фундамент
для removed/price-событий (2.4), триггеров «цена упала» (Фаза 7) и аналитики (Фаза 8).

### Фаза 4 — Резилентность планировщика + observability

Есть база: `WatchScheduler.runDaily` уже опрашивает подписки с изоляцией сбоев и
дайджест-доставкой. Добавляем резилентность и наблюдаемость маленькими шагами.
Тяжёлая инфра (прокси-бюджет, OTLP-экспорт, «поднять частоту») завязана на живой
деплой — уезжает в Фазу 5.

- **4.1 — Пейсинг скрейпа — сделано:** пауза `WATCH_MIN_DELAY_MS + random(WATCH_JITTER_MS)`
  между поллами в `runDaily` (последовательно, без knob на параллелизм — добавим,
  только когда упрёмся в скорость). Без миграций.
- **4.2 — Состояние подписки + автопауза на 403 — сделано:** колонка `pausedAt`,
  планировщик берёт только активные (`listActive`); Telegram `403` (заблокировал/удалён) →
  пауза подписок юзера (сбой записи не роняет прогон); `429` — плагином
  `@grammyjs/auto-retry`. Снятие с паузы: повторная отправка ссылки оживляет подписку
  (в `add()`); авто-unpause / команда `/resume` — позже.
- **4.3 — Детект «мёртвой» ссылки — сделано:** счётчик `consecutiveFailures` (только
  ошибки опроса, не «0 результатов» — иначе ложные срабатывания на узких поисках);
  N ошибок подряд (порог 5) → уведомить юзера «обнови ссылку» + автопауза подписки;
  сброс при успехе. Чистка `seen` уже покрыта prune до `MAX_SEEN_PER_SUBSCRIPTION`.
- **4.4 — Продуктовые метрики — сделано:** Prometheus counters (`nexo_deliveries_total`,
  `nexo_poll_errors_total`, `nexo_subscriptions_paused_total`) + gauges (`nexo_users`,
  `nexo_active_subscriptions`) через фасад `WatchMetrics`; инкременты в планировщике,
  снимок totals раз в прогон.
- **4.5 — Админ-команда `/stats` — сделано:** только для админа (`ADMIN_TELEGRAM_ID`,
  иначе молча игнор) — юзеры / активные / на паузе / последний прогон (`WatchStatus`).
- **4.6 — Алерты админу — сделано:** нотификация владельцу при каждой автопаузе
  (403 / мёртвая ссылка) с причиной; плюс алерт, если источник завалил все поллы за
  прогон (≥3, чтобы одна битая ссылка не поднимала ложную тревогу). Переиспользует
  админ-id (4.5). Экспорт ошибок в OTLP — Фаза 5.

### Фаза 5 — Деплой — **сделано** (детали инфраструктуры: [PRODUCT_TECH.md](PRODUCT_TECH.md))

Продукт работает 24/7 в проде. Что сделано (почему так — [PRODUCT_TECH.md](PRODUCT_TECH.md),
как это поднять — [DEPLOY.md](DEPLOY.md)):

- **Стек:** Hetzner CX23 + self-managed k3s (Oracle Always Free ARM не дали: out of capacity),
  managed Supabase (Neon не открылся), бесплатный egress-прокси на Oracle, Kustomize,
  multi-arch образ в GHCR. ~€6.5/мес, остальное $0.
- **Миграции при деплое** — initContainer'ом до старта бота (`migration:run:prod`; один
  `data-source.ts` работает и под ts-node, и в контейнере).
- **Секреты:** k8s Secret из семи значений (`npm run k8s:secrets`), копия у владельца —
  в KeePassXC. Зашифрованные секреты в git (SOPS+age) — ниже, «Осталось по фазе».
- **Безопасность БД:** TLS с проверкой сертификата, выключенный публичный Data API и RLS
  на всех таблицах — два независимых рубежа.
- **Один Deployment:** long-polling бот + in-process scheduler (singleton, `Recreate`).
  Отдельный scrape-CronJob и webhook — только под горизонтальное масштабирование.
- **CI/CD:** мерж `dev → main` (релиз) → тесты → образ по sha → джоба `deploy` выкатывает тот же
  коммит по SSH ключом, ограниченным одной командой.
- **Прокси на уровне источника:** kufar ходит через Oracle, realt — напрямую; новый источник →
  одна строка в адаптере.
- **Ошибки долетают до владельца:** продуктовые события — в Telegram (Фаза 4), любая ошибка
  приложения — в Sentry, с пользователем и тегами (репортер `telegram/report.ts`). Только
  ошибки, без трейсинга и профилирования — квота бесплатного тарифа не тратится зря.

незнакомую ссылку, а здесь остались инфраструктурные улучшения, которых никто, кроме владельца,
не замечает. Одно исключение — «поднять частоту проверок»: это скорость уведомления, её делаем
раньше Фазы 6.

- **Наблюдаемость: разделить админа и адресата алертов.** `ADMIN_TELEGRAM_ID` сейчас отвечает и
  за права на `/stats`, и за адрес алертов — вписать туда канал нельзя, `/stats` сломается. Ввести
  `ALERT_CHAT_ID` (по умолчанию = админ): тогда переезд алертов в канал/группу — смена переменной,
  без правок кода. Актуально, когда смотреть будет не только владелец.
- **Алерты уровня кластера.** Рестарты и недоступность пода не видит ни Sentry (он про ошибки
  работающего приложения), ни «сигнал жизни» (он ловит только полную смерть). Про
  crashloop, из которого под всё же поднялся, мы узнаем случайно.
- **Антибот (не гео):** `bid.cars` отдаёт `403` даже из РБ — решать при добавлении источника.
- **Бюджет прокси + backoff на бан** (из Фазы 4) — когда появится платный прокси.
- **Поднять частоту проверок** (раз в сутки → чаще) — скорость уведомления главное
  конкурентное поле. Заодно пересмотреть порог «мёртвой ссылки»: сейчас 5 неудач = 5 дней.
- **Окружения dev/prod:** рантайм-окружение по-прежнему **одно** — прод (деплой с `main`);
  `dev` тестируем локально. Полноценное второе окружение (два namespace + Kustomize overlays)
  требует отдельного бота (один токен = один поллер) и отдельной БД — отсюда и локальный прогон
  вместо стенда.
- **Позже, для обучения — Postgres в кластере.** Прод сидит на managed (Supabase), но
  для практики поднять свой Postgres в k8s — **сначала на dev-окружении** (не рискуем
  прод-данными): Deployment + **PVC** (постоянный том) + Service + пароль в Secret; затем,
  как следующий уровень, оператор **CloudNativePG** (бэкапы в object storage, PITR;
  HA/failover — на мульти-ноде). Отличный stateful-урок k8s. Переход обратим
  (`DATABASE_URL`), код не меняется.
- **Хранилище секретов у владельца — сделано 2026-09-06.** До этого значения жили только в
  кластере: пересборка или ошибочный `delete secret` → восстанавливать неоткуда. Выбран
  **KeePassXC** — отдельный файл базы изолирует проектные секреты от личных паролей, вложения
  принимают приватный SSH-ключ, бесплатен и офлайн. Состав записи и восстановление —
  [DEPLOY.md](DEPLOY.md) § «Где владелец хранит секреты». Синхронизацию в iCloud решили не
  включать (обоснование — в техническом бэклоге).
- **Позже — секреты в git (SOPS + age).** Сейчас секреты живут **только в кластере** и создаются
  скриптом (`deploy/secrets.sh`): пересобрал кластер — восстанавливай вручную из менеджера паролей.
  Это неудобство, а не потеря (каждый секрет перевыпускается в своей консоли), но правильно —
  хранить их **зашифрованными в git** рядом с манифестами: восстановление = `apply` из репозитория,
  история изменений видна. Ключ расшифровки — в менеджере паролей. ⚠️ Обратная сторона: потеря
  этого ключа делает зашифрованное нечитаемым, так что «сложнее» ≠ «безопаснее» автоматически.
  Естественно совмещается с GitOps-шагом ниже.
- **Позже, для обучения — GitOps (ArgoCD / Flux).** Сейчас деплой «пушим» из CI по SSH —
  для одного приложения это оправданно. Следующий уровень: оператор **внутри** кластера сам
  тянет желаемое состояние из git. Что это даёт: входящий доступ не нужен вовсе (никаких
  CD-ключей), кластер **сам исправляет расхождения** (кто-то поменял руками — вернётся к git),
  git становится единственным источником правды с готовым аудитом и откатом. Цена: ещё один
  сервис в памяти ноды и больше движущихся частей. **Делаем ради практики** — естественный
  момент: когда появятся dev/prod окружения (Kustomize overlays) и/или второй сервис.

### Фаза 5.5 — Синк с land-scraper: богатая карточка объявления — **сделано 2026-09-11**

**Что поехало:** контракт `Listing` получил координаты, продавца и `details` (подписанные
значения, которые заполняет адаптер); оба парсера их заполняют — kufar читает `ad_parameters`
человекочитаемыми метками и координаты (порядок `[lon, lat]`, проверено живьём), realt —
площади, год, этажность, контакт; карточка рисует всё это одним сообщением с экранированием и
обрезкой, которая никогда не режет цену и ссылку; доставка отправляет фото альбомом и пин на
карте, с откатом в текст при отказе медиа; первые 30 объявлений идут карточками, остаток — тем
же прогоном компактным списком.

**Чего сознательно не взяли из прототипа:** снапшоты на диске, конфиг фидов, сводку по фидам,
ретрай на 429 (у нас `@grammyjs/auto-retry`), пейсинг 3.1 с (он под каналы, у нас личные чаты),
предварительный резолв редиректов CDN kufar (в прототипе это нереализованный TODO — вместо него
откат в текст и лог кода ошибки). Детект изменения цены с правилом «обе валюты сдвинулись в одну
сторону на ≥2 %» — ценная, измеренная на живых данных вещь, но она относится к событиям
removed/price и ждёт таблицу `listings` (Фаза 2.4).

Решено 2026-09-06. В прототипе (`~/dp/my/land-scraper`) поведение и UX уже хорошие, а у нас
уведомление — это три строки: заголовок, цена, ссылка. Фото мы **парсим и выбрасываем**
(`kufar.parser.ts` заполняет `images`, формат их не читает), координаты не парсим вовсе.
Задача: пройти по прототипу и перенести всё, что имеет смысл, — начиная с **kufar** и
**telegram**-модуля. Берём поведение, не код: там код местами слабый, у нас другой контракт
(`SourceAdapter` вместо модуля на источник) и другой масштаб — много пользователей вместо
одного канала владельца.

- **Поля объявления.** В карточке прототипа: адрес, тип объекта, площадь, площадь участка,
  комнаты, год постройки, «удобства», продавец, дата — и **координаты** из `ad_parameters`.
  У нас в `Listing` только цена, адрес, описание, фото. Расширяем контракт и парсер kufar.
- **Фото.** `sendPhoto` для одного, media-group для нескольких, подпись в первом элементе,
  откат на текст при ошибке. Лимит подписи к фото — 1024 символа, не 4096.
- **Точка на карте.** Отдельным `sendLocation` после карточки; сбой пина не считается сбоем
  доставки — само объявление уже ушло.
- **Устойчивость отправки.** Троттлинг на чат (в прототипе 3.1 с), ретрай только на 429 с
  уважением `retry_after`, откат media-group → текст.

**Решено 2026-09-11: карточка на объявление, всегда — с фото и картой.** Вопрос стоял так: у
прототипа один канал владельца, поэтому там не жалко отдельного сообщения с фото на каждый
объект, а у нас доставка своя на каждого подписчика. Владелец выбрал полноту: пришло объявление —
пришли всё, что о нём известно. Ограничение по объёму: сотня карточек — это сотня сообщений и
минуты отправки одному человеку, а прогон идёт по подпискам последовательно и держит слот
опроса. **Сделано так:** первые `CARDS_PER_DELIVERY` = 30 идут карточками, остаток — тем же
прогоном компактным списком. Прежний потолок в 100 и обещание «…и ещё N — пришлю в следующую
проверку» удалены: отложенный хвост мог уехать за окно страниц и пропасть, поэтому всё
найденное уходит в том же прогоне.

**Как это делается generic** (иначе каждый новый плагин пришлось бы учить рисовать): у `Listing`
типизированное ядро — заголовок, ссылка, цена, адрес, дата, картинки, координаты — плюс
`details`, список подписанных значений, который заполняет адаптер. Он один знает, что у него
«Участок 12 сот.», а у авто было бы «Пробег 120 000 км», и задаёт порядок строк. Карточка рисует
ядро и детали как есть, ничего не зная про недвижимость, поэтому новый источник получает фото,
карту и полную карточку бесплатно. Цена решения: подписи деталей — русский текст, который
производит адаптер, то есть презентация слегка протекает в слой источников (учесть на шаге i18n,
см. Фазу 7). Числовые пост-фильтры по таким строкам не построить — они останутся на ядре (цена,
ключевые слова), а типизированное поле добавится тогда, когда фильтр действительно понадобится.

Порядок шагов: контракт и парсеры (сделано) → карточка текстом → фото и точка на карте →
доставка и потолок → тесты, доки, PR.

Засада, записанная в прототипе: CDN kufar (`rms.kufar.by`) отдаёт 302 на `rms8…`, и Telegram в
`sendMediaGroup` обрабатывает это непредсказуемо (`WEBPAGE_MEDIA_EMPTY`). Лечится резолвом
редиректа (HEAD) перед отправкой.

### Фаза 7 — UX-апгрейды

- **Кнопка «Показать ещё» для «Показать текущие»** — сама доставка дайджеста батчами сделана
  (см. `telegram.deliver.ts`), эта кнопка осталась.
- **Ручной запуск проверки для всех (решено 2026-08-19).** Сейчас `/check` в проде доступен
  только владельцу; сделать его пользовательским — «проверить мои поиски сейчас», не чаще раза
  в сутки, у админа без лимита. Закрывает главную слабость: ждать до утра. Что для этого нужно:
  **отвязать опрос от обработчика** (grammY разбирает обновления по одному, иначе один
  пользователь морозит бота для всех; **с Фазы 5.5 это уже не ~15 с, а минуты**: `/check`
  отправляет до 5 × (30 карточек + хвост), каждое сообщение с паузой в секунду), **колонка `users.lastManualRunAt`** (в памяти
  лимит обнулялся бы при каждом деплое), команда в меню и в `/help` — и там же честно сказать,
  что она **расходует** новые объявления (показанное завтра не придёт). Имя оставляем `/check`,
  подпись в меню — «Проверить сейчас». Ошибки ручного прогона по-прежнему не идут в счётчик
  «мёртвой ссылки». Общий слот опроса уже не даёт двум прогонам идти одновременно.
- **Обратная связь:** команда/кнопка «Написать в поддержку» и «Предложить идею»
  (сообщение уходит владельцу / в issue-трекер). **Это же закрывает адрес для запроса удаления
  данных** — обещание в `/help` сейчас без канала (см. § 2 «Приватность» и бэклог).
- Уточнить копи baseline: «сейчас N (это база, не шлю); новые буду присылать».
- Выбор event-типов на подписку.
- Частота на подписку: instant (~15–30 мин) / daily digest; **тихие часы** (не слать ночью).
- Пост-фильтры на подписку: min/max цена, ключевые слова, «только с фото»;
  ценовые триггеры («цена ниже X / упала на N%»).
- «Избранное»: следить за конкретным объявлением (цена/снятие); кнопки на карточке
  уведомления — ⭐ избранное / 🙈 скрыть.
- Индикатор здоровья в `/list`: «проверено сегодня 09:00, новых: 2» у подписки.
- Приватность: `/delete_me` (удалить все свои данные) + экспорт подписок.
- Валютное предпочтение BYN/USD на юзера.
- **Deep-links** (`t.me/bot?start=…`): кнопка «Поделиться поиском» (подписка в 1 тап),
  реферальный трекинг источников юзеров; связка с постами каналов.
- **Подтверждать тишину раз в неделю** (идея из прототипа, `common/quiet-summary.service.ts`).
  Сейчас прогон без новых объявлений не пишет ничего, и пользователь не может отличить тихий
  рынок от сломанного бота — а у нас проверка раз в сутки, то есть молчать можно неделями.
  В прототипе это решено так: пустой прогон копит счётчик тишины, и раз в неделю уходит одно
  сообщение «за неделю ничего нового, тишина с такого-то числа, текущие итоги». Ключевая
  оговорка оттуда: ошибки и алерты о здоровье источника **не** идут через этот канал, иначе
  недельный отчёт превращается в обещание, которого он не держит.
- **Месячное подтверждение**: одно сообщение со списком подписок, «✅ Оставить все» /
  выборочно; нет ответа N дней → автопауза + возврат одной кнопкой (экономит скрейпинг).
  Позже — спрашивать только неактивных.
- **Цель доставки на подписку** (`deliveryTarget`): личка | свой канал | группа+топик
  (бот-админ сам заводит топик на подписку). Тот же механизм — для кураторских каналов.
- **Публичные кураторские каналы** (владелец): авто-постинг подборки по фикс-ссылке
  в публичный канал (напр. «Участки Гродно») → набор подписчиков → монетизация
  рекламой (Фаза 9). Параллельно с личными подписками.
- Telegram Mini App.
- **i18n / переводы:** сообщения бота переведены на русский под аудиторию беты (строки лежат
  прямо в коде, `users.language` уже пишется при подписке). **Плюс с Фазы 5.5 часть
  пользовательского текста производят адаптеры** — подписи деталей карточки («Участок»,
  «Год постройки») задаются в `sources/*/`, потому что только адаптер знает словарь своей
  вертикали. Это осознанная цена generic-контракта, но на этом шаге её придётся учесть:
  пользовательские строки живут не в одном месте. Дальше — язык профиля: собрать строки
  в одном месте, ключи вместо литералов, добавить английский. `NOTE` стоит в
  `telegram.handlers.ts` у константы `PROMPT`. Учесть при этом: спеки сейчас сверяются с самой
  прозой (~20 мест в трёх файлах), поэтому любая правка формулировки роняет тесты, а сплошная
  замена по файлам уже один раз испортила названия тестов и согласование чисел. На этом шаге
  правильный порядок — сначала вынести строки в именованные константы и импортировать их в тесты,
  потом менять сами тексты. Ключ заводить не всякой строке, а по читателю (подход io-proxy,
  `docs/services/translations/`): человек читает и может на это отреагировать → ключ; диагностика,
  логи и текст для машин остаются английскими без ключа — их переводом мы только лишим себя
  возможности искать сообщение по тексту.

### Технический бэклог

Отложено осознанно — сделать при ближайшем касании соответствующего кода.

Отложенные мажоры зависимостей и пин `multer` — итоги обновления **2026-09-09** (остальное
поднято до последних версий; проверено фактическими peer-диапазонами, не по памяти):

- **NestJS 12 — ждём экосистему.** Ставится только через `--legacy-peer-deps`: `@nestjs/throttler`
  (latest `6.5.0`, релиза под Nest 12 вообще нет) и `@sentry/nestjs` (latest `10.73.0`, Nest 12
  только в prerelease `11.0.0-beta.*`) объявляют peer `^11`. Это rate limiting и репортинг ошибок — оба
  патчат внутренности Nest и ломаются **молча**, так что форсировать нельзя. Аргумента
  «зато закроем advisory» тоже нет: `@nestjs/platform-express@12` пинит **тот же** `multer@2.2.0`
  (уязвимости закрыты отдельно, через `overrides`). Вернуться, когда throttler и Sentry объявят
  `^12`; тогда же разобрать переход ядра Nest на ESM (наш билд — CommonJS).
- **TypeScript 7 — упирается в тулчейн, не в наш код.** `ts-jest` держит peer `<7`,
  `typescript-eslint` — `<6.1.0`. Единственная версия, которую принимают все, включая
  `@nestjs/schematics@12` (`>=6`), — `6.0.x`; на неё и поднялись. Поднимать TS 7 можно только
  после того, как ts-jest и typescript-eslint выпустят поддержку. Из-за `<6.1.0` у
  typescript-eslint каретка была бы шире реально поддерживаемого, поэтому у `typescript`
  диапазон `~6.0.3` (патчи 6.0.x берёт, в 6.1 не уходит) и запись в `PINNED_ALLOWLIST`
  (`scripts/lint/check-package-versions.js`) — единственное исключение из правила «все
  зависимости через `^`». Вернуть каретку вместе с поддержкой в ts-jest и typescript-eslint.
- **`overrides` на `multer` — почему он есть и когда его снимать.** `@nestjs/platform-express`
  пинит `multer@2.2.0` ровной версией, а в ней четыре high-advisory (три DoS, одна — обход
  лимита размера файла); через все зависящие от неё пакеты Nest это давало 10 находок
  `npm audit`. Обновление Nest не помогает: в `@nestjs/platform-express@12` тот же `2.2.0`,
  поэтому единственный путь — `overrides`. Multipart-загрузок у нас нет нигде, так что в нашем
  коде advisory были недостижимы: это гигиена дерева, а не закрытие живой дыры. Диапазон
  `~2.3.0`, а не `^`: мы перебиваем **точный** пин чужой зависимости, и дрейф в чужом пути
  загрузки файлов нам не нужен. Снять, когда `platform-express` начнёт пинить `>= 2.3.0`.
- **`@types/node` остаётся на `^24` при latest `26`.** Типы обязаны совпадать с рантаймом, а он
  Node 24 (`.nvmrc`, `node:24-alpine` в `Dockerfile`, `engines.node >=24`). На 26 компилятор
  начнёт пропускать вызовы API, которых в Node 24 нет, — ошибка уедет из сборки в прод.
  Поднимать вместе с базовым образом, одной задачей.

  `apply -k` его перенимает и перезаписывает, а смонтированный сертификат подхватывается
  только при перезапуске пода. Содержимое совпадает байт в байт, так что делать ничего не
  нужно — но сам факт перехода нигде не описан.
- **Окружения GitHub заведены, но не используются.** `development` и `production` существуют
  без правил защиты и без привязки к веткам; в каждом лежит `SCRAPER_API_KEY`, которого нет
  нигде в коде. Решить: если ключ живой — это висящий доступ (никто не пользуется, никто не
  следит), удалить или задействовать. Заодно окружения — способ усилить гейт перед
  прод-деплоем: сам гейт теперь есть (прод едет только с `main`, мерж `dev → main` ручной), но
  привязка джобы `deploy` к окружению `production` с правилом «нужен подтверждающий» и
  ограничением по ветке добавила бы вторую пару глаз и защиту от случайного push в `main`.
  Переносить CD-секреты при этом не нужно: джоба с `environment:` видит и репозиторные, и
  окружения; окружение переопределяет только при совпадении имени.
- **Место `report.ts`.** Лежит в `modules/telegram/`, но импортирует `SourceUnavailableError`
  из `modules/sources/` — сквозная забота внутри одного модуля. Пока потребитель один, это
  нормально; появится второй (не-telegram) — переносить в `common/`.
- **ConfigMap через `configMapGenerator`.** Сейчас у ConfigMap фиксированное имя, поэтому
  `apply -k` правит его на месте, и автооткат деплоя (`rollout undo`) конфиг не возвращает —
  откатывается только шаблон пода. С `configMapGenerator` имя несёт хеш содержимого, версия
  конфига едет внутри шаблона пода и откатывается вместе с ним.
- **Health-путь захардкожен в двух файлах.** `/api/v1/health/{live,ready}` прописан в
  `HEALTHCHECK` образа (`Dockerfile`) и в трёх пробах `k8s/deployment.yaml`, а реально
  собирается из `API_PREFIX`/`API_VERSION` в ConfigMap. Рассинхрон → пробы стучатся в 404,
  k8s считает живой под мёртвым и перезапускает его по кругу. Сейчас держится на
  комментариях-предупреждениях. (`docker-compose.yml` путь не дублирует — наследует
  `HEALTHCHECK` образа.)
- **Копия базы паролей — только на ноутбуке владельца.** Самый низкий приоритет в списке.
  Секреты и SSH-ключ продублированы в KeePassXC (состав записи — [DEPLOY.md](DEPLOY.md)
  § «Где владелец хранит секреты»), но сам `.kdbx` лежит рядом с оригиналами, поэтому сценарий
  «ноутбук утонул» не закрыт. **Решено 2026-09-06: так и оставляем** — шесть из семи значений
  отзываемы по таблице внутри самой записи, цена восстановления — вечер возни, а не потеря
  проекта. Закрывается переносом `.kdbx` в синхронизируемую папку (iCloud): файл зашифрован
  мастер-паролем, провайдер видит только шифротекст.

Привнести позже:

- **Богатая карточка: поля, фото, точка на карте, устойчивая отправка** — Фаза 5.5 выше.
- **Детект removed / price-change** (правило «обе валюты изменились») — Фаза 2.4.
- **kufar: перейти на официальный search-API** (`api.kufar.by`, как в land-scraper)
  вместо HTML — легче и стабильнее.
- **Лестница загрузки для защищённых сайтов** (`common/scraping/`, 10 файлов кода): обычный запрос →
  локальный браузер (`rebrowser-puppeteer`) → цепочка платных провайдеров, причём каждый
  источник объявляет только те ступени, которые для него измеримо работают (браузер не пробивает
  WAF av.by — значит эта ступень там просто не объявлена). Оттуда же два дорого выученных урока:
  ступень считается успешной только если тело прошло предикат «это та страница, а не заглушка», и
  наружу надо отдавать **первую настоящую** ошибку цепочки, а не последнюю — три дня простоя
  bamper списывали на «закончилась квота», хотя причина была в 422 от другого провайдера двумя

  ступени противоречат правилу «только бесплатные тарифы», так что из лестницы возьмём
  бесплатные — предикат пригодности и локальный браузер.
- **Измеренная экономика бесплатных тарифов провайдеров** — шапка `common/scraping/scraping.module.ts`.
  Если для источника за Cloudflare всё-таки понадобится провайдер, этот комментарий экономит день
  исследования: порядок цепочки там выстроен по стоимости, а не по возможностям, и каждая цифра
  измерена живьём. Коротко: ScraperAPI считает запросы (1000/мес), но на бесплатном тарифе не

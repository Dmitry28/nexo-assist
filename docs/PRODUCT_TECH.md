# Product Tech — что где живёт и почему

Технический паспорт продукта: из чего он собран в рантайме, какие приняты решения и
какие есть ограничения. Как поднять/задеплоить — в [DEPLOY.md](DEPLOY.md) (учебный гайд +
runbook). Что делает продукт — в [PRODUCT.md](PRODUCT.md). Куда движемся — в
[PRODUCT_PLAN.md](PRODUCT_PLAN.md).

> **Репозиторий публичный.** В актуальных файлах репозитория **нет** IP-адресов, токенов и
> идентификаторов (один адрес остался в истории git — см. «Учебный инцидент» в DEPLOY.md) —
> только роли компонентов. Реальные значения: консоли провайдеров, `~/.ssh`, Secret'ы
> кластера (см. «Где лежат реальные значения»).

## Топология

```
Telegram ──long-polling──►┐
                          │   Hetzner (CX23, Ubuntu, k3s)
realt.by ◄────напрямую────┤   ├─ Pod: initContainer «migrate» → контейнер бота
                          │   └─ ConfigMap + Secret + Service (ClusterIP)
kufar.by ◄─через прокси───┤              │
   ▲                      │              └──TLS(verify-full)──► Supabase (managed Postgres)
   └── Oracle Always Free (E2.1.Micro) + tinyproxy: egress для источников,
       которые блокируют хостинги (сейчас kufar). Доступен только с нашего сервера.

GHCR (ghcr.io) ──образ (multi-arch, пин по sha)──► кластер
```

## Доступность источников (важное продуктовое ограничение)

Проверено эмпирически (запрос одной и той же страницы с разных точек):

| Источник     | Из Беларуси | Hetzner (ЕС)               | Oracle (ЕС) | GitHub Actions | Вывод                                        |
| ------------ | ----------- | -------------------------- | ----------- | -------------- | -------------------------------------------- |
| **realt.by** | 200         | **200**                    | 200         | —              | работает напрямую                            |
| **kufar.by** | 200         | **403** «Доступ ограничен» | **200**     | 200            | блокирует **диапазоны хостингов**, не страну |
| **bid.cars** | **403**     | 403                        | —           | —              | **антибот** (не гео) — отдельная задача      |

**Вывод:** блокировка kufar — не по геолокации (Польша через VPN и Azure/GitHub тоже
проходят), а по чёрному списку хостинг-провайдеров.

**Решение — прокси на уровне источника.** Адаптер объявляет `useProxy: true` (сейчас только
kufar), транспорт (`sources/scraping/http.ts`) подставляет адрес из `SCRAPE_PROXY_URL`. В проде
эта переменная **обязательна**: без неё kufar пошёл бы напрямую, получил `403`, и это выглядело
бы как блокировка источника — счётчик мёртвой ссылки автопаузил бы живые подписки с ложным
«проверь ссылку». Поэтому приложение просто не стартует.
Следствия: добавить прокси новому источнику = одна строка в его адаптере; сменить прокси
(другой VPS, VPN-шлюз) = одна переменная; остальные источники и Telegram идут напрямую.

| GitHub Secrets                 | `CD_SSH_KEY` (ключ деплоя, умеет только запустить deploy.sh), `CD_HOST` (адрес), `CD_HOST_KEY` (сам ключ публичный, но по нему сервер находится в публичных сканах — то есть выдал бы адрес)                                                                                                                                                                                                                                                                                                                                                                |

**Публичный API провайдера отключён + RLS.** Supabase, помимо обычного подключения к Postgres,
поднимает **HTTP-API к таблицам** (PostgREST), рассчитанный на браузерные приложения — то есть
доступный всем, у кого есть адрес проекта и публичный ключ. Наш бот им не пользуется (ходит
напрямую по `DATABASE_URL`), поэтому: (1) Data API в проекте **выключен** — путь доступа убран
целиком; (2) на всех таблицах включён **RLS** без разрешающих правил (миграция
`EnableRowLevelSecurity`) — если API однажды включат обратно, он не отдаст ни строки.
Приложению это не мешает: подключение идёт ролью-владельцем таблиц, а владелец RLS не подпадает.
Проверено на реальной БД: владелец видит строки, посторонняя роль — 0, её `DELETE` затрагивает
0 строк.

**Список таблиц в миграции — не единственная защита.** RLS не является частью описания
сущностей, поэтому `migration:generate` её не создаёт и об её отсутствии не сообщает: новая
таблица приехала бы незащищённой, и никакой сигнал бы не сработал. Поэтому e2e-тест
([`test/watch.e2e-spec.ts`](../test/watch.e2e-spec.ts)) спрашивает у самой базы: есть ли в
публичной схеме таблицы **без** RLS — и есть ли хоть одна политика доступа. Второе так же важно:
защита работает именно потому, что политик нет; разрешающая политика оставила бы флаг включённым,
а доступ открыла. Обычная таблица без RLS уронит CI, а не приведёт к письму от провайдера через
полгода. Остаётся щель: для материализованных представлений RLS в Postgres нет вообще, так что
проверить их нечем — если такое появится, доступ к нему закрывать отдельно.

**TLS к базе:** проверка сертификата включается через `sslmode=verify-full` в `DATABASE_URL`.
Supabase использует **свой** корневой CA, которого нет в публичном списке Node → его
сертификат лежит в репозитории ([`k8s/db-ca-configmap.yaml`](../k8s/db-ca-configmap.yaml)) и
включается переменной `NODE_EXTRA_CA_CERTS`
(одна переменная покрывает и приложение, и initContainer с миграциями — без кода).
**Срок действия CA — до 2031-04-26.** Истечение = не деградация, а отказ: первым падает
initContainer миграций, под не доходит до Running, а симптом (`SELF_SIGNED_CERT_IN_CHAIN`)
не отличим от ошибки конфигурации. Замена — скачать новый в панели провайдера.

## Как узнаём об ошибках

Четыре уровня, каждый ловит своё:

1. **Продуктовые события → в Telegram владельцу** (Фаза 4): автопаузы (403 / мёртвая ссылка),
   падение источника. Это то, на что нужно реагировать по продукту.
2. **Ошибки, задевающие пользователя → Sentry с контекстом.** Кто (telegram-id), где случилось и
   по какой ссылке. Sentry считает **уникальных пользователей на проблему** — видно «эта ошибка
   затронула N человек», и можно написать конкретному. Три тега, у каждого одно значение:
   - **`kind`** — чья вина: `source` (сайт не отдал пригодный HTML — не ответил, вернул ошибку
     или прислал слишком большой ответ; не наш баг, но объём важен) против `bug`
     (наш дефект). Определяется по типу ошибки (`SourceUnavailableError`), а не по тексту
     сообщения, чтобы классификация не разъезжалась.
   - **`action`** — где: `subscribe` / `check` / `show-current` / `bot-update` / `daily`.
   - **`op`** — какая операция упала, когда `action` этого не говорит (например `mark-seen`).
3. **Любая ошибка приложения → Sentry** (`SENTRY_DSN`, опционально; без него репортинг выключен).
   Ловим: необработанные исключения и rejection'ы (перед выходом ждём отправку — иначе самый
   важный отчёт не успеет уйти), HTTP 5xx в глобальном фильтре и **намеренно проглоченные**
   ошибки прогона (сбой опроса/доставки/записи). Последнее принципиально: мы их глушим, чтобы
   один битый источник не рушил прогон, — значит обязаны сообщить о них наружу. Сбой отметки
   «показано» ищется по `op: mark-seen`: доставка прошла, но объявления остались непомеченными —
   тот же дайджест уйдёт снова на следующем прогоне.
   Sentry группирует одинаковые ошибки, поэтому 500 повторов ≠ 500 уведомлений.
4. **Приложение умерло целиком** (OOM, падение ноды, зависание) — **«сигнал жизни»**: раз в
   5 минут приложение пингует внешний сторож (`HEARTBEAT_URL`, healthchecks.io), сторож молчание
   замечает сам и присылает тревогу владельцу (канал настроен на его стороне — сейчас почта). Единственный класс отказов, который Sentry не
   ловит по определению: мёртвый процесс отчёт не отправляет. Проверка живёт **снаружи**
   кластера — внутренняя умерла бы вместе с приложением; входящих портов не нужно, что важно при
   схеме без ingress. Переменная не задана — механизм выключен, и приложение говорит об этом
   ошибкой в логе при старте.

Метрики (Prometheus) — отдельная история: они про «сколько», а не «что сломалось».

**NOTE:** Sentry SDK сам поднимает OpenTelemetry, поэтому `SENTRY_DSN` и
`OTEL_EXPORTER_OTLP_ENDPOINT` одновременно включать нельзя (при обоих в лог пишется warning).

## Как код попадает в прод

1. Мерж в `dev` (интеграция) → **CI** (GitHub Actions): lint/typecheck/тесты/миграции/e2e.
   Деплоя отсюда нет — проверяем локально, затем мержим `dev → main`; этот мерж и есть релиз.
2. **Сборка образа**: amd64 и arm64 собираются параллельно, каждый на раннере своей
   архитектуры, и сшиваются в один multi-arch-тег → пуш в GHCR с тегами `sha-<commit>`,
   имя ветки, `latest` (на `main`).
3. Деплой: в `k8s/kustomization.yaml` образ **пиннится по sha** (неизменяемый тег — видно,
   что запущено, и откат = прежний sha) → `kubectl apply -k k8s/`.
4. В поде: **initContainer `migrate`** применяет миграции (идемпотентно, TypeORM хранит
   применённые) → только потом стартует бот. Упали миграции → под не поднимается.
5. Под не стал готов за 180 с → **автоматический откат** (`rollout undo`) на предыдущую рабочую
   версию, джоба красная. Реплика одна и стратегия `Recreate`, поэтому без отката неудачный
   деплой оставил бы бота лежать. Откат возвращает приложение, **не** схему БД — см. DEPLOY.md.

**Деплой автоматический (CD).** Мерж `dev → main` → тесты → сборка образа → джоба `deploy` заходит
по SSH ограниченным ключом и выкатывает тот же коммит ([`deploy/deploy.sh`](../deploy/deploy.sh)).
API кластера наружу не открыт, kubeconfig в GitHub не хранится. Подготовка хоста —
[`deploy/setup-server.sh`](../deploy/setup-server.sh) (идемпотентный; он же нужен при переезде).

## Доступ и сетевая безопасность

- **SSH** — **только по ключу** (вход по паролю отключён), плюс `fail2ban` (5 неудач за 10 мин →
  бан на час): сервер видит ~40k попыток подбора пароля в неделю просто как часть фонового
  сканирования. Настройки живут в `deploy/setup-server.sh` (шаг 6), а не в ручных правках.
  Файрвол провайдера пускает извне **только 22** — закрыть его по списку IP нельзя, через него
  ходит CD с GitHub Actions (широкие диапазоны раннеров).
- **API кластера (6443) наружу закрыт**; управление — через **SSH-туннель** с локальной машины
  (`kubectl` → localhost:6443 → по SSH → кластер). Туннель поднимать с
  `ServerAliveInterval`, иначе «мёртвый» туннель даёт `TLS handshake timeout`.
- **Прокси на Oracle** закрыт двумя рубежами: сетевой фильтр (OCI Security List + iptables —
  порт 8888 только с IP нашего сервера) и basic-auth на самом прокси. Открытый прокси в
  интернете находят и начинают абузить за часы.
- Контейнеры: non-root, read-only rootfs, drop all capabilities, ресурс-лимиты.

## Известные ограничения и что дальше

- **Одна реплика, без HA** — и причин две, причём главная не поллер. `WatchStatus` (слот
  опроса) — булево в памяти процесса, поэтому кроны двух реплик стартуют одновременно, обе
  считают «новое» по одному и тому же `seen` до того, как хоть одна его запишет, и пользователь
  получает каждое объявление дважды. Плюс long-polling требует одного поллера (второй получает
  409). Падение ноды = простой до перезапуска. Масштабирование → общий лок на прогон + webhook.
- **kufar работает только через прокси** (Oracle). Прокси лежит → kufar-подписки уходят в
  автопаузу (детект «мёртвой ссылки») + алерт админу; realt продолжает работать.
- **Supabase free засыпает** при простое — первый запрос после паузы медленнее.
- **Бэкапы БД — свои.** У провайдера на free-тарифе их нет (проверено в панели 2026-09-05).
  Ночной `pg_dump` из кластера ([`k8s/backup-cronjob.yaml`](../k8s/backup-cronjob.yaml)): 7
  последних дампов на диске ноды, успешный дамп пингует вторую проверку сторожа. Не покрыта
  одновременная потеря ноды и базы — для этого копия у владельца (`npm run k8s:backup:fetch`).
  Зачем именно так и как восстанавливать — [DEPLOY.md §4.3c](DEPLOY.md).
- **Только prod-окружение.** `dev` тестируем локальным запуском; отдельный стенд (второй бот +
  своя БД + Kustomize overlays) — позже.
- **Ошибки видны в логах и продуктовых алертах**, но сквозной сбор ошибок (OTLP + правила
  алертинга) ещё не подключён.
